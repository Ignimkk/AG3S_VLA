## 무엇을 했나 (평이한 요약 먼저)

`--target-extent attention-surface` 의 표면 선택을 GPU 로 옮겼다. 선택 과정은 surface graph, support plane, seed, ROI, solve, code 영상이다. 새 flag `--attention-surface-device cuda` 로 켜며 기본은 꺼짐(cpu)이다. 꺼져 있으면 고정된 study 코드가 그대로 돌고 GPU module 은 import 되지 않는다.

T76 표면 방식이 기록한 요청 487 개 전부에서, 같은 process 의 CPU 와 GPU 결과가 완전히 같았다.
- 선택 node 집합 IoU: 최소 1.0
- code 영상 pixel 일치: 최소 1.0
- 기록 field 15 종: 모두 같음

표면 선택 시간은 중앙 697 ms · p95 768 ms (T76 server 기록, CPU) 에서 중앙 43–46 ms · p95 83–105 ms (GPU 독점 측정 두 번) 로 줄었다. 목표 p95 ≤ 150 ms 를 넘지 않는다.

계산 대부분은 GPU 에서 돈다: 역투영, voxel node, edge, 법선용 1-ring 합, RANSAC inlier 수, seed · ROI, code 영상.
- 선형 방정식 풀이 (`ifg_graph.solve` 의 `spsolve`) 와 영역 선택 (`ifg_round.region_gate`) 은 **고정 함수를 host 에서 그대로 부른다.** 지금 남은 시간의 대부분이 이 host solve 다.

### CPU 와 계산 순서가 다른 곳 (알려진 차이)

| 단계 | CPU (고정 코드) | GPU | 결과 영향 (T76 487 요청) |
|---|---|---|---|
| 역투영 | `backproject` | `device_recon.backproject_device` (T38 B4, numpy 1.26.4 dgemm 과 비트 동일) | 없음. node 수 · 순서 487/487 같음 |
| node 중심 | `np.add.at` (pixel 순) | 정렬 뒤 `segment_reduce` (결정적, 합 순서 다름) | ulp 수준. 선택 · centroid 기록 같음 |
| 1-ring 합 (법선) | 전체 node 의 sparse 곱 | ROI node 만 `index_add_`. 공분산이 같으면 `eigh` 가 같다 | ulp 수준 |
| support refit | inlier 점의 SVD `vh[-1]` | 3×3 scatter 행렬 `eigh` 최소 고유벡터 | `n_support_nodes` 487/487 같음 |
| RANSAC inlier 수 | dgemm 블록 (server 에서는 이미 `auto` → GPU `dot3`) | `dot3` 전부 GPU (폭 1 블록도) | 같음 |
| ROI | `cKDTree.query(distance_upper_bound)` | bbox 로 먼저 거른 뒤 제곱거리 `< r²` (블록 ≤ 2^24 원소) | `n_roi` 487/487 같음 |
| code 영상 | `_pixel_nodes` 로 pixel → node 를 다시 유도 | build 의 pixel → node 를 그대로 씀. 기록 `pixel_node_keys = "build"` (CPU 는 `"centroid_keys"`) | pixel 487/487 같음 |

- 기록 key: cuda 일 때 CPU 기록의 key 를 모두 담는다. 더해지는 key 는 `device = "cuda"` 와 `ms_detail` (build_nodes · build_edges · build_support · solve_gpu · solve_host) 이다.
- `ms` 의 key (build · solve · codes · total) 는 같다. 단 GPU 의 `solve` 에는 seed eligibility 계산이 들어 있다 (CPU 는 build 와 solve 사이 측정 밖).

## 동등성 (통과 조건: IoU 중앙 ≥ 0.99 · 최소 ≥ 0.95, code pixel 일치 ≥ 0.99)

입력은 T76 SURF 5 group 의 487 요청이다 (`t78b_inputs.py`). 짝짓는 방법은 T76 `t76_metrics.py:100-104` 와 같다: chunk 와 T74 client 의 `step_*.npz` 를 t_step 순서대로 위치로 짝짓는다.
- depth: `step_*.npz` 의 1 mm uint16 / 1000. server 는 다시 렌더한 float depth 를 받았지만, 이번 비교에서는 CPU 와 GPU 가 같은 depth 를 받는다.
- robot mask: server 가 기록한 code 영상 == 0 (구 mask · 무효 pixel). T76 SURF 는 `--robot-mask` 없이 돌았으므로 구 mask 다.
- server 가 기권한 19 요청 (`no_region`, code 영상 미기록) 은 robot mask 를 0 으로 두었다. 그래서 이번 재계산에서는 487 개 모두 선택이 났다. 이것은 CPU · GPU 같은 입력 비교용이다.
- 참고: CPU 재계산 대 server 기록 code 영상의 일치는 중앙 1.0 · 최소 0.954 다. depth 양자화 차이이며 CPU · GPU 비교와는 무관하다.

## 시간 (§3.1 item 6: 표면 선택 p95 ≤ 150 ms)

조건: GPU 는 `gpu_lock exclusive`, BLAS 1 thread (server `--blas-threads 1` 과 같음), 요청마다 1 회, warm-up 뒤에 쟀다. H200 NVL 이다.

- 독점 run 1 의 tail: total > 150 ms 가 22 요청이다 (max 511). 모두 HURDLE_B 의 **연속된 한 구간** (ep850 k=26–33, ep211 k=0–13) 에 몰려 있다.
  - 이 구간에서는 GPU 단계와 host 단계가 모두 약 90 ms 단위로 늘었다.
  - 같은 요청이 동등성 run 에서는 26–63 ms 였다.
  - pod 의 CPU quota 는 `cpu.max 1600000/100000` (16 CPU) 이고 load average 는 약 54 다.
  - 그래서 CFS throttling 으로 process 가 멈춘 것으로 판단한다 (추정. run 1 동안의 throttle 계수는 재지 않았다).
- 독점 run 2 는 throttle 계수를 앞뒤로 남겼다 (`nr_throttled` +6, `throttled_usec` +22.3 s). 이 run 에서 > 150 ms 는 0 개, max 107 ms 다.
- warm-up (`serve_safe` 시작 때 한 번): 0.7–1.0 s (jiterator kernel 이 disk cache 에 있을 때). cache 가 비어 있으면 첫 compile 이 5–22 s 걸렸다. warm-up 뒤 첫 실제 요청은 42 ms 였다. warm-up 장면이 선택까지 가지 않았던 첫 판에서는 첫 요청이 527 ms 였다. 그래서 warm-up 은 선택이 나지 않으면 예외를 낸다.

## 내가 기대하는 결과
