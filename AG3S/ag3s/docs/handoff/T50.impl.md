## 무엇을 했나 (평이한 요약 먼저)

HSR (Hidden-state Sub-task Recognition: frozen VLA prefix feature `kv_L4` 위의 linear probe 로 pick / place / home 을 읽는 것) 의
instruction 둔감이 (a) probe 학습 · (b) representation · (c) 16D LoRA fine-tuning 중 어디서 오는지 가르는 계산을 만들었다.
T48 의 feature cache 를 그대로 읽어 ① prompt 교체에 feature 가 얼마나 움직이는지 (C1 대 C1p 거리 비 `r`, text 절반 · image 절반),
② C1 변형 (distractor 지시 → 정답 `pick`) 을 학습에 넣은 counterfactual probe 를 episode 단위 교차검증으로 학습 · 평가하고,
②′ text 만 · image 만 · label 섞음 통제를 같은 경로로 돌린다 (T50a, CPU).
T50b 용으로 `pi05_base` 를 **16D config 의 transform 그대로, params 만 바꿔** 같은 변형의 feature 를 뽑는 GPU extract stage 와,
train split C0 · C1 추출 · base 대 LoRA 비교표 stage 를 구현만 해 두었다.

CPU 에서 확인한 것 (구현 점검이지 결과가 아니다): numpy/scipy 로 다시 쓴 LogReg 가 SUBTASK-b train 에 C = 0.01 로 맞추면 `kv_L4_v1` 과
val accuracy 0.9807766 동일 · 확률 최대 차 2.0e-5 · coef 최대 차 2.2e-6. 두 checkpoint 의 parameter tree 가 각자 load 될 model 과
shape 까지 일치 (LoRA 71/71, base 51/51) 하고 두 경우의 input transform chain 이 같다 (metadata 만 읽음).

## 1. 사전 고정 정의 — 코드에서 어떻게 되어 있나

| ① 기준선 | `d_adj` = 같은 episode 의 **다음 sampled frame** (stride 6 = 0.4 s) 의 C0 와 이 frame C0 의 상대 L2. 마지막 frame 은 없음 (NaN) | 같은 함수 |

### params 만 바꾸는 방법 (`t50_extract.load_base_policy:83`)

1. 같은 train config `pi05_rby1_randomized_pick_place_16d_lora` 를 가져와 **model 의 Gemma variant 두 개만** non-LoRA 이름으로 바꾼다:
   `gemma_2b_lora → gemma_2b`, `gemma_300m_lora → gemma_300m` (`train_config_for:68`). 두 variant 는 width · depth · head 가 같고 LoRA 쪽에 `lora_configs` 만 더 있다 (`gemma.py:79-107`).
   `return_attn_probs=True` 는 T48 `load_policy` 와 같게 둔다 (`pi05_attention.py:59-68`).
2. `pi05_base/params` 는 **우리 LoRA 학습의 초기 weight** 다: `config.py:1139-1141` `CheckpointWeightLoader("gs://openpi-assets/checkpoints/pi05_base/params")`.
   base 를 LoRA model 에 넣지 않는 이유: LoRA adapter 는 0 초기화가 아니다 (`lora.py:20` normal(0.01), `lora.py:51-52` 의 `lora_a` · `lora_b` 둘 다) —
   `CheckpointWeightLoader` 처럼 빠진 adapter 를 model 초기값으로 채우면 (`weight_loaders.py:50-54`, `_merge_params:76-104`) base 에 무작위 adapter 가 더해진다.
3. `create_trained_policy(cfg, pi05_base, norm_stats=…)` (`policy_config.py:16-25`): model 은 `cfg.model.load(restore_params(pi05_base/params, bf16))` (`:57`;
   `model.load` 는 tree · shape 검사, `model.py:233-241`). base 에 `assets/` 가 없으므로 **norm stats 는 LoRA checkpoint 의 `assets/` 에서 명시적으로 넘긴다**
   (`:59-64` 는 `norm_stats is None` 일 때만 checkpoint 에서 읽음) — 같은 quantile 통계 → 같은 state 문자열.
4. data config (`cfg.data.create`) 는 바꾸지 않은 config 에서 나온다: `AlohaInputs(adapt_to_pi=False)` → `DeltaActions` (action 에만) → quantile `Normalize`
   → `InjectDefaultPrompt` → `ResizeImages(224)` → `TokenizePrompt(discrete_state_input=True)` → `PadStatesAndActions(32)` (`config.py:130-141`).
   model transform 이 보는 것은 `model_type` (= `PI05`, `pi0_config.py:57-60`), `max_token_len` 200, `discrete_state_input` True, `action_dim` 32 — 모두 variant 와 무관.
5. **CPU 점검 (`--stage check-params`, 실행함)**: `nnx.eval_shape` (메모리 할당 없음) 로 만든 model 의 param tree 와 각 checkpoint 의 `_METADATA` shape 비교 →
   LoRA config × LoRA ckpt 71/71 일치, base config × base ckpt **51/51 일치, 빠진 key 0 · 남는 key 0 · shape 불일치 0**. transform chain (객체 주소를 지운 repr)
   두 경우 동일 (`transforms_equal: true`). 기록: 내 smoke run 의 `verify/T50/check_params.json`.

### prefix feature 가 action dim 과 무관한 이유

- `kv_L4` 는 `AttentionSampler._prefix` 의 KV cache 에서 나온다 (`pi05_attention.py:95-105`): `model.embed_prefix(obs)` → `PaliGemma.llm([tokens, None], …)`.
  **두 번째 expert (action expert) 입력이 `None`** 이라 action expert 는 돌지 않는다. reduction 은 layer 4 · head 0 의 V (`:107-123`).
- `embed_prefix` (`pi0.py:108-139`) 가 쓰는 것은 `obs.images` (SigLIP) 와 `obs.tokenized_prompt` 뿐이다. `obs.state` · action 은 `embed_suffix` (`pi0.py:142-188`) 에서만 쓰이고,
  pi05 는 state token 도 없다 (`pi0.py:153` `if not self.pi05`). `action_in_proj` 는 `:161` (suffix) 에서만.
- 16D state 는 prefix 에 **문자열로만** 들어간다: `TokenizePrompt` 가 `PadStatesAndActions` **앞에** 있으므로 (`config.py:136-140`) state 문자열은 정규화된 16 개 숫자다
  (`tokenizer.py:22-29`, T48 token check 에서 decode 확인). 32 로의 padding 은 문자열 뒤라 prefix 에 영향이 없다.
- 그리고 실제로 **dim 불일치가 없다**: 두 checkpoint 모두 `action_dim` 32 (`pi0_config.py:25`), `action_in_proj [32, 1024]`. 16D action 은 학습 때 32 로 padding 되었다.

### verifier · lead 가 알아야 할 차이 (판정 아님, 사실)

- LoRA 학습에서 무엇이 바뀌었나 (freeze filter, `pi0_config.py:93-122`): `.*llm.*` 의 base weight 는 고정, **LoRA adapter · SigLIP (`img`) 전체 · action/time projection 은 학습됨**.
  따라서 base 와 LoRA 의 prefix 차이 = SigLIP fine-tune + gemma_2b (prefix expert) LoRA adapter. token embedding (`llm/embedder`) 은 고정이었다.
- base 는 RBY1 의 16D state 정규화를 본 적이 없다. 문자열 형식 `Task: …, State: …;\nAction: ` 은 pi05 의 discrete state 형식 그대로지만 숫자의 의미는 base 에게 새 것이다.
  "base 가 16D 입력 변환과 맞지 않아 feature 가 무의미" 인지는 T50b 결과 (base C0 정확도 등) 로 verifier 가 본다 (task 의 되돌아올 지점).
