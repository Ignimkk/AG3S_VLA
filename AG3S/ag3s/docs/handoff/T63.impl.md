## robot config 를 어떻게 지었나 (같은 270 sphere 라는 증거)

- **sphere**: snapshot 의 `build_constraint_robot_model` 을 server 와 같은 flag 로 호출했다 (`--links gripper --sphere-spacing 0.4 --max-spheres-per-capsule 32 --capsule-radius-scale 0.05 --finger-cover both`). 그 결과 `UrdfSphereChain._local_spheres` (link, link-frame centre, radius) 를 그대로 cuRobo `collision_spheres` 에 넣었다.
  - 검증 (`robot_spec.json` 의 `checks`): n = 270 = record. radii 최대 차 3.3e-10 m. link 이름 순서도 record `sphere_link_names` 와 같다.
  - cuRobo 는 sphere 를 link 순서로 묶는다. 그래서 `sphere_permutation` 으로 우리 index ↔ cuRobo index 를 매핑한다.
- **URDF**: `snapshot/robots/rby1/description/models/rby1a/urdf/model.urdf` (md5 는 dev checkout 과 같다).
- **base_link = `link_torso_5`.** torso 6 관절은 최적화하지 않지만 chunk 마다 `q_now` 로 바뀐다. 10 episode 에서 torso_0 가 최대 0.0215 rad 변하고, 손 위치로는 약 20 mm 다. cuRobo 는 lock joint 를 build 시점의 fixed transform 으로 굳히므로, torso 를 lock 하면 한 chunk 의 자세에 묶인다. 대신 **world 를 torso_5 frame 으로 옮겼다**: grid pose = `inv(T_base_torso5) · T_base_grid`, `T_base_torso5` 는 baseline FK 로 계산한다. 정확한 rigid transform 이다.
- **c-space** = `left_arm_0..6, right_arm_0..6` (chunk column 순서). 우리 TO 의 최적화 관절과 같다.
- **finger 4 관절**: 우리 TO 에서 finger 는 FK parameter 다 (측정 개도 · step 별 envelope). cuRobo 에서는 `lock_joints` 를 0 에 두고, finger sphere 를 prismatic axis 방향으로 `v` 만큼 옮겨 넣는다 (`kinematics_params.update_link_spheres`, in-place 라서 CUDA graph 가 그대로 본다).
  - 근거: `T(v)·p = T(0)·(p + axis·v)` 이므로 joint 값 `v` 와 정확히 같다 (unit test 로 확인).
  - parity 에서는 step 별 envelope 값을 그룹별로 적용했다 (chunk 당 그룹 최대 14).
  - B0 solver 는 chunk 당 **한 값** (step 0 = 측정값) 만 쓴다. server envelope 가 plan window 안에서 이 값과 벌어지는 정도는 `export_manifest.json` 의 `finger_path_plan_drift_mm_max` 에 있다: episode 별 최대 3–36 mm (사과 놓기 · 열기 구간), 0.5 mm 넘는 chunk 는 episode 당 3–33 개.
  - solver 의 rollout 10 개 transition model 은 전부 한 `link_spheres` tensor 를 공유한다. 그래서 update 한 번이 모든 rollout 에 닿는다 (GPU 에서 확인).
- **limits**: TO effective limit 을 메모리에서 덮어썼다 (`apply_limits`): position = model_xml ± 0.02 rad margin, velocity · acceleration = URDF × 0.9 (snapshot `build_limits`). jerk 는 cuRobo 기본 500 rad/s³ 이다 (우리 TO 에는 jerk limit 이 없다).

## ESDF → cuRobo 매핑 (frame / origin / sign)

| 항목 | AG3S record | cuRobo v2 | 처리 |
|---|---|---|---|
| frame | robot `base` (`frames.jsonl` `frame_id: base`) | solver base = `link_torso_5` | chunk 마다 grid pose 를 torso_5 frame 으로 바꾼다 (`grid_pose_in_frame`) |
| origin | voxel (0,0,0) 의 **중심** | `pose` = grid 상자의 **중심**. voxel `i` 의 중심 = `pose + (i − n/2 + 0.5)·vs` | `pose = origin + (n−1)/2·vs` (`grid_centre`, cuRobo 식을 다시 써서 unit test 로 확인) |
| index | `(nx,ny,nz)` C order, z 가 가장 빠름 | `voxel_idx_to_flat = x·ny·nz + y·nz + z` | 재배열 없이 flat 으로 복사 |
| sign | 안 −, 밖 + | `compute_local_sdf`: "negative inside, positive outside" | 부호를 뒤집지 않는다 (`get_occupied_voxels` 는 쓰지 않는다) |
| dtype | float16 | float16 (`VoxelData.features`) | bit 그대로 |
| 격자 밖 | 우리 field: `outside_distance` = +0.5 m (`unknown_policy free`) | `max_esdf_distance` (10000, 충돌 없음). 경계에서는 in-bounds corner 만 가중한다 | parity 에서 경계 row 를 따로 집계했다 (차이 없음) |
| 층 | coarse 20 mm + fine 5 mm (main 합성), free (target 제외 fine) | 층마다 VoxelGrid 하나 | cuRobo 는 obstacle cost 를 **합산**한다. parity 는 층을 하나씩 켜서 재고 우리 2-tier 규칙 (`compose_main`) 으로 합성했다 |

- signed distance 를 꺼내는 방법: cuRobo kernel 은 `w·act(r + η − sdf)` 만 돌려준다. `w = 1`, `η = 20 m` 로 질의하고 activation 을 역산했다 (`sdf_from_activation_cost`). float32 역산 오차는 0.02 mm 미만이다 (unit test).
- **B0 world** = record `esdf_free_*` 한 층, 모든 sphere 공통 (task 0.2).

## dt 처리 (fixed 1/15 vs resample)

- cuRobo 는 매 pass 마다 trajectory 를 vel / acc / jerk limit 에 맞춰 time-optimal 로 re-time 한다. `FixedDtTrajectoryOptimizer` 는 `compute_trajectory_dt` 만 override 해서 고정 dt 를 돌려준다 (상속만 사용). 결과 spline 은 정확히 3.333 s 에 걸쳐 있고 goal 에서 끝난다.
  - 실측: start 오차 1e-7 rad, chunk 끝 goal 오차 1.2e-7 rad, `solution_state_dt` = 0.033333.
- **cuRobo 의 dense interpolation 출력은 쓸 수 없었다.** `calculate_traj_steps` 의 `nearest_int` 가 knot 당 sample 수를 반올림해서, 16 knot × 1/6 s 에서 61 sample (1/15 s 로 표시) 이 나온다. 3.33 s spline 을 4.07 s 로 늘린 셈이다. 그래서 첫 debug 에서 index 50 의 goal 오차가 0.03 rad 였다.
- 그래서 출력은 **optimizer state grid (`js_solution`)** 에서 읽는다:
  - `exact` (기본): n_knots 21 × interpolation_steps 4 → 101 state, 1/30 s. 짝수 state 가 곧 15 Hz chunk step 이다. **재샘플이 없다.** 유일한 변경은 n_knots 16 → 21 이다.
  - `resample16`: cuRobo 기본 16 knot → 81 state, 1/24 s. t = k/15 로 선형 재샘플한다.
  - 두 결과를 다 저장했다. 어느 쪽을 비교 기준으로 쓸지는 lead 가 정한다.

## λ 배선

- `scaled_weights(weights, λ)` 가 `w_track`, `w_continuity`, `w_deflection_rate` 만 λ 배 한다. 나머지 키 (`w_smooth`, `w_slack`, `track_decay`, `servo_accel*`) 는 그대로다. λ ≤ 0 · inf · NaN 은 거부한다.

- 확인: test 가 세 가중치가 정확히 λ 배인지, 항의 cost 값이 λ 에 선형인지 (λ 100 = 100 × λ 1), 후보가 13 개 (B0 1 + 4 × 3) 인지 본다. 각 후보의 `weights_used` 와 `settings.changes_from_default` 가 `curobo_step3.json` 에 있다.

## 열린 문제 · 한계

1. **cuRobo 결과가 solve 이력에 따라 달라진다.**
   - 같은 순서로 다시 돌리면 bit 단위로 같다 (smoke r2 vs r3: 13 후보 × 8 chunk 차 0).
   - 그러나 앞선 chunk 의 결과가 바뀌면 뒤 chunk 도 바뀐다. λ=1 B0 · B1 은 no-free chunk (#320–#360) 에서만 world 가 바뀌었다. 그런데 그 뒤의 free chunk ep211 #735 가 단계 2 와 0.12 · 0.16 rad 다르다. 이 chunk 는 모든 변형이 실패하는 chunk 다.
   - 원인은 확인하지 않았다. cuRobo optimizer 내부 상태 (L-BFGS buffer 등) 로 추정한다.
   - 그래서 전체 실행의 chunk 순서를 고정한다: episode 오름차순, chunk 오름차순, 후보마다 같은 순서. 결과를 "chunk 독립" 으로 읽으면 안 된다.
2. **solver 13 개를 동시에 살려 두고 chunk 를 바깥 loop 로 돌리면 cuRobo 안에서 CUDA error 가 났다** (`operation not supported on global/shared address space`, 둘째 chunk 의 6 번째 solver; log `step3_prep/smoke/curobo/run_step3_curobo.log`). 그래서 단계 2 처럼 한 번에 solver 하나만 둔다. 원인은 확인하지 않았다.
3. **prefetch 를 켜면 시간이 부풀어 오른다.** 다음 record 를 background thread 로 읽으면 B0 warm wall median 이 71 ms 다 (끄면 59 ms, 단계 2 는 53 ms). 그래서 `--prefetch` 는 기본 off 이고 timing 실행에서 쓰지 않는다. smoke r2 는 prefetch 를 켰고 궤적은 r3 와 같다.
4. **look-ahead tail.** 평가기는 plan16 의 tail step (8–15) 에도 실행 창 규칙을 쓴다. TO 는 tail 에서 target · 지지면이 최근접인 행을 빼고 잰다 (`_lookahead_keep`). 그래서 `to_recorded` · `to_resolved` 의 plan16 clearance 는 TO 자신의 tail 기록보다 낮게 나올 수 있다. exec8 은 TO 가 인증한 값과 같다 (충실도 검사).
5. **`to_recorded` 의 시간** 은 server 의 live CPU 측정 (`to.solve_ms`, 정책 추론과 같은 머신에서 잰 것) 이다. `to_resolved` 는 이 머신의 offline CPU 측정이다. 둘 다 GPU 시간과 같은 표에 놓지 않는다.
6. 재풀이 `chained` 의 남은 차이 (최대 17 mm, HOLD 구간 뒤) 는 위 표에 있다. 기록 refined 와 재풀이 중 어느 것을 "우리 TO" 의 주 행으로 쓸지는 lead 판정이다. 기록이 실제로 실행된 쪽이다.
7. 단계 2 의 한계는 그대로다: B4 margin 규칙이 우리 TO 보다 보수적이다. cuRobo 쪽 finger 열림은 chunk 당 한 값이다 (평가기는 step 별 값). self-collision 은 끈다.
8. 평가기는 attached 질의점이 있는 chunk 를 처리하지 않는다 (`build_scene` 이 멈춘다). 이 10 episode 에는 그런 chunk 가 0 개다.
