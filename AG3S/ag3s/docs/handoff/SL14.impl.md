# SL14 — 구현: 정답 latch (`--oracle-latch`, KO) 와 PLACED 재장전 (`--placed-rearm`, rearm)

> writer: ag3s-implementer · 읽는 쪽: verifier, scribe, lead · 2026-11-05 · worktree `wip/sl14-oraclelatch` (base feature/panda-benchmark 240fa5df)
> `--oracle-latch` 는 진단 전용(채택 후보 아님), `--placed-rearm` 은 배포 가능(정답을 쓰지 않음). 둘 다 기본 꺼짐, Panda 서버만.

## 무엇을 했나 (평이한 요약 먼저)

**KO (`AG3S-final-panda-v3-e0to-pc-oraclelatch` = pc판 + `--oracle-latch`).** client 가 요청마다 MuJoCo 정답 `ag3s/oracle_grasp = {held, target_body}` 를 보낸다
(`held` = SL12 와 같은 target 물체의 geom 이 왼손가락·오른손가락 geom 둘 다와 `data.contact` 로 접촉 중). 서버는 증거 latch 를 평소대로 갱신한 **뒤에**
latch 를 정답에 맞춘다: 정답 held 인데 latch 가 HELD 가 아니면 attach(쥔 물체가 거리장에서 빠지는 것은 정상 attach 와 같다), 정답 not held 인데 HELD 면
detach 하고 `searching` 으로 돌린다(다시 쥐기 허용). HELD 동안 증거의 회수(`attach_revoked`)·놓음·slip 판정은 정답이 여전히 held 이면 무효다(ag3s 는 detach 를 받지 않는다).
call 마다 `panda/grasp.oracle = {held, overrode: "attach"|"detach"|null, evidence_state, ...}` 를 기록한다.

**rearm (`AG3S-final-panda-v3-e0to-pc-rearm` = pc판 + `--placed-rearm`).** latch 가 PLACED 이고 측정 개도가 열려 있으면(≥ `gripper_closed_below`) SEARCHING 으로
돌아간다. 대상 잠금은 그대로라 다음 `update` 가 LATCHED 로 올리고, 닫힘 시도 → HELD 는 평소 증거 검사를 그대로 거친다. 그 call 의 `panda/grasp.rearm = true`.

## 쥔 물체 id 는 어떻게 정하나 (KO)

AG3S 는 물체 목록을 따로 갖지 않는다(지각 기억에 "손에 가장 가까운 물체"를 고르는 길이 없다). 그래서 정답 attach 의 기하는 다음 순서로 고른다:
1. `ag3s.manipulated` (T20 조작 대상 후보, latch 의 `manipulated_id` 와 같은 것)가 쓸 만하면 그 `geometry`
2. 아니면 latch 가 잠근 이름과 일치한 마지막 target (`SafePolicy._latched_target`)
3. 아니면 직전 call 의 attention target (`_last_constraint_set.target`)
없으면 attach 하지 않고 `grasp.oracle.attach_failed` 에 이유를 남긴다. 사용한 출처는 `grasp.oracle.held_source`.
**reach 문(12 cm)은 묻지 않는다**(`reach=None`; 정답이 손가락 사이라고 말한다) — 잰 거리는 `grasp.oracle.reach_mm`. `AG3S.attach` 의 허용 가능성 검사(가장 좁은 폭 ≤ 최대 개도)는 그대로 남아
거절되면 `attach_failed` 에 기록된다. 즉 **ATS 가 틀린 물체를 target 으로 잡았으면 정답 attach 도 그 물체를 붙인다**(정답은 "쥐었다" 만 알려준다, 어느 지각 군집인지는 모른다).
`target_body` 는 기록용이다.

## verifier 가 알아야 할 것

- 새 flag: `--oracle-latch`, `--placed-rearm` (serve_safe, 기본 꺼짐, Panda 서버만), client `--oracle-grasp` (기본 꺼짐). 꺼짐이면 서버 argv · 응답 · 기록 키 · 요청이 이전과 같다.
  (`LatchConfig` 에 필드 `placed_rearm` 이 생겼지만 이를 dump 하는 곳은 없다.)
- 재생산이 필요한 산출물: 없음.
- 옛 기록과 호환: 깨지지 않는다. `panda/grasp` 에 `oracle` / `rearm` 키가 해당 판에서만 생긴다.
- **정답 attach 는 reach 문을 건너뛴다.** 정답 held 이지만 ATS 의 target 후보가 손에서 멀리 있는 call 은 팬텀 구가 손에 붙는다(`grasp.oracle.reach_mm` 로 확인). 기제 판정(task §2 "실제로 쥔 call 중 latch HELD ≥ 0.95") 은 latch 상태만 보고, 붙은 구가 실제 물체와 겹치는지는 `held_source` · `reach_mm` 으로 따로 봐야 한다.
- 정답 held 가 계속 참인 동안 증거 latch 는 HELD 분기를 계속 돌려 매 call 에 `suppressed_detach` 를 기록할 수 있다(증거가 release/revoke 를 말했지만 무효가 된 call).
- 정답 not held 이고 latch 가 PLACED 이면(증거가 놓았다고 한 뒤) 서버는 SEARCHING 으로 돌린다(`rearmed_from_placed`) — 정답 모드에서 PLACED 는 흡수 상태가 아니다.
- 측정 시점: 정답은 observe 시점(마지막 env.step 직후, 요청의 이미지 시점)의 `data.contact` 이다.

## 위험

1. 정답 attach 의 기하가 ATS 가 고른 물체이다(위). 틀린 군집이면 정답 모드에서도 틀린 물체가 붙는다.
2. `held` 정의는 "target geom 이 양 손가락과 접촉"이라 얇은 테두리를 한 손가락 pad 와 손바닥으로 쥔 경우 False 가 된다(그 경우 HELD 였던 latch 가 detach 된다). 정의는 task 문서 그대로.
3. rearm 은 PLACED 직후 개도가 열려 있으면 바로 SEARCHING 이 된다(release 판정이 열림 프레임을 요구하므로 거의 항상 다음 call). 놓은 뒤 빈손 닫힘이 증거 검사를 통과해 거짓 attach 되면 `attach_revoked` 가 회수한다(평소 경로와 같다).
4. 이 worktree 에서는 서버 CPU build · GPU 를 돌리지 않았다(요청대로). 실제 server 시작 · LIBERO client 접속은 검증하지 않았다 — SafePolicy 수준과 py3.8 client 수준에서 각각 시험했다.
