T63 (offline 비교, `T63.task.md` · `T63.verify.json` · `AG3S_T47_LOG.md` T63 절) 의 후속 접미사 STEP.

## 목적

offline 에서는 명령 궤적만 잴 수 있었다. 이번에는 cuRobo v2 B0 를 서버의 TO 자리에 넣어 실제로 실행하고,
같은 장면 · 같은 seed 의 VLA 단독 (E0) · 현재 방식 (C1aN, 우리 TO) 과 짝지어 **실제 궤적 (measured_qpos) 기준
접촉**과 작업 성공을 본다. 성공률 표본이 아니라 약 10 episode 의 빠른 확인이다. 어느 쪽이 낫다고 미리 정하지 않는다.

## 구현 (implementer)

1. **서빙 코드 기준 = C1aN snapshot tree `f0d8046` (`<IFG-APPLE run>/snapshot/`).** 거기에 T63 의 `AG3S/trajopt/curobo_v2/`
   와 TO backend 전환 flag (예: `--to-backend curobo-b0`, 기본 off) 만 더한 새 snapshot 을 만든다. **flag off 일 때 C1aN 과
   동작이 같아야 한다** (기존 test + 기록 1 chunk 재현으로 확인). working tree 의 다른 세션 미커밋 flag 를 섞지 않는다.
   snapshot 은 IFG 방식대로 `<새 run>/snapshot_cr0/` + `snapshot_cr0_head.txt` (tree hash · 방법).
2. **서버 argv 는 C1aN 과 같고 `--to-backend curobo-b0` 만 추가.** cuRobo 는 서버 process (`.venv-openpi-live`, cuRobo
   0.8.0.post1.dev43 import 확인됨) 안에서 돈다.
3. **cuRobo B0 설정은 T63 offline B0 와 같게**: 같은 270 sphere robot · `link_torso_5` base (world 를 torso 로 옮김) · composed world
   (상자 안 `esdf_free`, free 층이 없으면 `min(coarse, fine)`, 상자 밖 coarse) · goal = 그 chunk 의 `reference_chunk[-1]` (cspace) ·
   seed = reference · timing `exact` · self-collision off · 우리 TO 의 joint 한계. 입력은 record 배열 대신 **서버가 그 chunk 에 만든
   live field · q_now · finger 열림** (record 에 쓰는 것과 같은 값).
4. **TO 자리만 바꾼다.** 우리 TO 의 SQP 대신 cuRobo 가 chunk 를 내고, 그 뒤의 **인증 검사 (전체 행 clearance, 같은 contact
   policy) · HOLD · 상태 보고는 우리 refiner 의 기존 경로를 그대로** 쓴다. cuRobo 50 step 출력을 refined chunk 로 쓴다.
5. 서버 시작 시 cuRobo warm-up (CUDA graph capture 약 4 s) 을 episode 전에 끝낸다. solver 하나를 episode 내내 유지하고,
   chunk 마다 cuRobo solve ms · success · failure reason 을 constraint record 와 log 에 남긴다.
6. CPU unit test + **1 episode smoke (ep126, 대조 장면)** 까지. 10 episode 실행은 verifier 가 한다.

**B0m 의 여유 규칙** (우리 TO 와 같게)
- 우리 TO 는 최근접 표면이 비-target 장애물 · support plane 인 행에 `max(그 행 margin, obstacle_margin)` 을 준다. target 행은 면제한다 (`config.py:781–812` snapshot).
- B0 world 에서는 상자 안 target 이 이미 제외되어 있어, 남는 표면이 모두 비-target 이다. 그래서 world 거리 전체에서 0.010 m 를 빼면 같은 규칙이 된다.
- 다르게 처리해야 하는 행이 있으면 implementer 가 보고한다.

**물리 clearance 정의 (사전 고정)**
- 같은 평가기에서 `obstacle_margin` · contact margin (`manipulated_link_margin`) 을 0 으로 둔 signed distance.
- target 행의 면제 (권한 있는 손가락이 target 에 닿는 것) 는 contact policy 그대로 둔다.
- 실행 구간 (8 step) 과 plan window (16 step) 별로, 물리 관통 chunk 수 · 최소 clearance median / p5 / min 을 보고한다.

**smoke 통과 기준 (사전 고정)**
- crash 없음.
- episode 끝까지 이어지는 HOLD 정지 (끝에서 연속 HOLD ≥ 20 chunk) 없음.
- 성공 여부는 통과 기준이 아니다 (결과로 보고).
