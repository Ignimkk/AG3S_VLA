# SL11 fork — LIBERO-Safety 응답 모델 (`--response-model libero_safety_fork`) — 구현

> writer: ag3s-implementer · 2026-11-05 · branch `wip/sl11-fork` (base main 66b2c14f) · 읽는 쪽: verifier, scribe, lead

## 무엇을 했나 (평이한 요약 먼저)
LIBERO-Safety env의 fork OSC 컨트롤러가 명령 action에 어떻게 따라가는지(1차 지연 `y_t = α y_{t-1} + β x_t`)를 VLA 단독 LIBERO-Safety 기록
(`sl7-liberosafety-vla30-*vla_only`, 30 episode)에서 맞췄다. 서버에 새 flag `--response-model {robosuite141, libero_safety_fork}`를 두어,
`libero_safety_fork`이면 변환 C(정 · 역)와 TrajOpt action 상자 · 적용된 명령 되돌림이 이 모델을 쓴다. 기본 `robosuite141`은 지금과 bit 동일하다.
모든 Panda 판 `X`는 `X-lsfork`로 돌릴 수 있다(`profile.register_lsfork`). **LIBERO-Safety에서 돌릴 이름: `AG3S-final-panda-v3-e0to-pc-lsfork`.**

**먼저 알려야 할 것:** 맞춘 fork 모델은 (client의 `libero_to_safety` 축척을 넣은 서버 단위로) robosuite 1.4.1 모델과 **크게 다르지 않다**
(아래 표). `outputs/2026-11-05_Panda_기본설정_점검` 항목 4의 "위치 약 3.5배 · 회전 약 8배 overshoot(계산)"는 이 데이터로 확인되지 않는다.
이 모델 교체만으로 큰 개선을 기대하기는 어렵다. 판정은 verifier의 closed-loop에 맡긴다.

## 기록(npz)이 담고 있는 것 — 단위 근거
- `episodes/*.npz`의 `action`은 **client `adapt_action` 전의 정책 action(LIBERO 척도)**다. `env_action`은 저장되지 않는다
  (`libero_safety_client.run_episode`: `rec.step(action, ...)`; `env_actions`는 `rec.env_actions`일 뿐 npz 키에 없음).
  run manifest의 `action_adapter = libero_to_safety` → fork가 받은 값 `x_fork = g · action`, `g_pos = 0.05·0.2494/1.0 = 0.012472`,
  `g_rot = 0.5·0.2484/1.0 = 0.124224`(`REALISED_GAIN`; 같은 값을 `fit_response.GAINS_LIBERO_TO_SAFETY`가 가지며 test가 client 상수와 대조).
- `obs_robot0_eef_pos/quat`(wait step 포함, `is_wait`로 표시), `action_chunks`, `chunk_t`(= 호출 시점의 loop `t` = obs 인덱스).
- 맞춤은 fork 자체 단위(`x_fork`)로 하고(그래야 `steady_state_gain`이 fork의 실제 이득, ≈1), 서버 단위는
  `β_server = β_fork · g / scale`(scale = 0.05 / 0.5)로 옮긴다. α는 그대로. 이 변환 덕에 `action.py`의 식(`x = 0.05 a`, `Dx/scale`)은 그대로이고,
  서버가 낸 `a`를 client가 `g`배 해서 fork에 주면 의도한 경로가 실현된다.

## 맞춤 결과 (`robots/panda/description/osc_response_fit_libero_safety_fork.json`)
방법은 `outputs/verify/SL5a/scripts/fit_osc_response.py`와 같다(성분 공유 계수 최소제곱, wait step 제외). 차이는 **trimmed fit** 하나다.
plain OLS는 R² 0.879(위치)·0.686(회전)로 관문(0.9)에 못 미쳤다. 원인은 전체 step의 약 4–6 %(명령 7 mm인데 실현 10 mm 같은 step; 접촉 · 놓침 사건으로 보이며 컨트롤러 응답이 아님)다.
그래서 잔차가 4σ(MAD) 넘는 step을 반복 제거한다(6회). **두 R²를 모두 기록**했고 관문은 trimmed R²로 읽는다는 점을 verifier가 판단해 달라.

| | α | β (fork 단위) | 정상 이득 | R² (trimmed) | R² (전 step, 같은 계수) | plain OLS R² | 제거 step | β_server (서버 단위) |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 위치 | 0.6655 | 0.3241 | 0.969 | **0.973** | 0.878 | 0.879 | 4.1 % | 0.0808 |
| 회전 | 0.8335 | 0.1565 | 0.940 | **0.942** | 0.674 | 0.686 | 5.8 % | 0.0389 |

robosuite 1.4.1(서버 단위): 위치 α 0.7169 β 0.0706, 회전 α 0.8747 β 0.0311 → fork/1.4.1 비: 위치 β 1.14배 · 회전 β 1.25배, 정상 이득 비 0.97 · 0.94.
전 step 1-step 예측 R²: 위치 1.4.1 0.879 vs fork 0.878, 회전 0.665 vs 0.674 — 이 기록으로는 두 모델이 구별되지 않는다.
회전 명령은 정책이 거의 안 쓴다(|a| < 0.3이 99.9 %); 큰 회전 보정은 외삽이다. 위치는 |a|<0.05 구간에서 유효 β가 모델의 0.76배, 0.6 이상에서 1.01배(약한 비선형).

## offline 관문 (task §2) — 5 step 뒤 예측 EE − 실제 EE
chunk 시작에서 `y_{-1} = p_t − p_{t−1}`로 시작해 정책 chunk의 앞 5행에 모델을 적용(전방 예측과 같은 식), 5 step 뒤 실제 EE와 비교. 중앙값(p90).
`python -m AG3S.adapters.panda.fit_response gate --fork <json>`.

| 기록 · 모델 | 위치 오차 mm | 회전 오차 rad | chunk 수 |
|---|---:|---:|---:|
| LIBERO-Safety VLA 단독 · (a) robosuite141 (현재) | **4.79** (p90 16.1) | 0.0109 (0.0335) | 2513 |
| LIBERO-Safety VLA 단독 · (b) fork | **4.39** (p90 15.4) | 0.0100 (0.0325) | 2513 |
| LIBERO VLA 단독(`sl5f-libero10-init0`) · robosuite141 | 5.32 (p90 9.4) | 0.0133 (0.0296) | 241 |
| task 기준(LIBERO 통과 chunk, 이전 측정) | 4.7 | | |

- (b) 4.39 mm ≤ 4.7 mm → **관문 통과**(R² ≥ 0.9도 trimmed 기준 통과). (a)는 4.79 mm로 기준 4.7을 약간 넘는다. 개선폭은 0.4 mm로 작다.
- 이 지표는 정책 chunk가 매끈해 지연 모델에 둔감하다(TO 보정 chunk가 아니다). 4.7 mm는 이전 측정 값이며 같은 코드로 재현하지 않았다(같은 방식으로 LIBERO 기록을 재면 5.32 mm).
  보정 chunk에서 모델이 얼마나 맞는지는 이 offline 기록으로 알 수 없다 — fork에서의 TO 보정 기록이 필요하다.

## 서버가 fork 모델을 쓰는 조건 (검출 가능 → 거절 구현)
- `--response-model libero_safety_fork`이면 `ChunkToJointPolicy.infer`가 요청의 `panda/action_adapter == "libero_to_safety"`를 확인하고 아니면 `ValueError`(요청 거절).
  이 키는 LIBERO-Safety client만 보낸다(`pi05_libero` 체크포인트 기본 `libero_to_safety`; `pi05_libero_safety`는 `none` → 거절). 일반 LIBERO · SafeLIBERO client는 키가 없어 거절된다.
- 기본 모델은 키를 보지 않는다. LIBERO-Safety client 요청에 키 하나(`panda/action_adapter`)가 늘었다 — 서버는 `panda/` 접두 키를 정책에 넘기기 전에 떼므로 기존 판의 동작은 같다(기본 모델 test).
- 변환 mode B(`AG3S_PANDA_CONVERSION=B`)의 역변환은 지연을 쓰지 않아 전방 예측에만 fork 모델이 영향을 준다. C(pc판)가 대상이다.

## verifier 가 알아야 할 것
- 새 flag: `--response-model`(기본 `robosuite141`, 이전과 bit 동일). 기록 키는 fork일 때만 `info["response_model"]`, 판 기록 `response_model`도 그때만.
- 재생산 산출물: fit json은 `python -m AG3S.adapters.panda.fit_response fit --out ...`으로 다시 만든다(입력 = storage VLA 단독 기록).
- 옛 기록과 호환: 깨지지 않음(레지스트리의 기존 판 hash 불변).
- GPU / server는 띄우지 않았다. closed-loop 효과는 미측정.

## 내가 기대하는 결과
(verifier는 측정 전에 읽지 않는다.) fork 모델 판이 pc판 단독보다 크게 나아질 것으로는 기대하지 않는다 — 두 모델의 차이가 작다(β 14–25 %). 큰 차이는 응답 모델 밖(접촉 · 보정 크기)에서 나올 것이다.
