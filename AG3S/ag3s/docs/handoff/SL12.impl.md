# SL12 — 구현: 정답 target(시뮬레이터 segmentation) 진단, RB-Y1 T46e visible-target oracle 의 Panda 이식

> writer: ag3s-implementer · 읽는 쪽: verifier, scribe, lead · 2026-11-05 · worktree `wip/sl12-oracle` (base main 5f473482)
> 진단 전용, 기본 꺼짐. 채택 후보가 아니다.

## 무엇을 했나 (평이한 요약 먼저)

RB-Y1 에서 만든 "visible-target oracle" 을 Panda LIBERO · LIBERO-Safety 에서 쓸 수 있게 했다. client 가 MuJoCo 가 이미 그리는
geom-id segmentation 을 **code 영상** (0 로봇·없음 / 1 정답 target / 2 정적 / ≥3 다른 움직이는 물체) 으로 바꿔 요청마다 싣고,
서버는 RB-Y1 과 같은 `OracleMemory` · `oracle_visible_split` 으로 target 의 보인 면 + truncation 띠를 target-free 층에서 지운다
(`--target-extent oracle-visible --oracle-extent-identity gt`). 새 판 두 개:
`AG3S-final-panda-v3-e0to-pc-oraclegt` (pc판 기준), `AG3S-final-panda-v3-e0to-pc-mi10-oraclegt` (pc-mi10 기준).
launcher 는 이 두 판에서만 client flag `--oracle-segmentation` 을 자동으로 붙인다. 꺼짐이면 요청 · 기록 키 · registry 가 이전과 같다
(test 로 보임). SafeLIBERO 는 이번에 하지 않아 launcher 가 거절한다.

## 정답 target 을 고르는 법 (suite 별, 실행 설정에 찍힘)

`benchmark/adapters/libero_panda/oracle_codes.py: choose_target` — env 의 `parsed_problem` (BDDL) 을 읽는다.

1. BDDL `:goal` 의 **첫 predicate 중 첫 인자가 움직이는 물체 (`:objects`)** 인 것의 그 인자.
   - LIBERO Spatial / Object / (10): `On/In A B` → A. SL3 의 `task_target.goal_roles` 와 Spatial · Object 전 BDDL 에서 일치 (test).
     LIBERO Spatial 은 `akita_black_bowl_1` 이 target, `plate_1` · `akita_black_bowl_2` · `cookies_1` · ramekin 은 code ≥ 3.
   - LIBERO-Safety: `Checkgrippercontactpart A (..)` → A (affordance: knife_1 · hammer_1 · classic_blue_mug_1 · frypan_1 ·
     fork_1), human_safety `On akita_black_bowl_1 left_hand_1` → bowl, obstacle_avoidance `In white_yellow_mug_1 ...` → mug.
2. 없으면 첫 움직이는 `:obj_of_interest`.
3. 없으면 (fixture 만 건드리는 goal: `Open cabinet`, `Turnon stove`; LIBERO Goal 의 일부) client 가 시작 거절.

한계: "put both A and B" 류는 첫 물체가 episode 내내 target 이다 (둘째를 옮길 때 target 이 둘째로 바뀌지 않는다).
robot = `robot0_* · gripper0_* · mount0_*` body, 나머지 비-물체 (table · floor · fixture) = 2.

### 판 정의와 flag 선택 이유
`-pc-oraclegt` = pc판 − `--nontarget-evidence surface` + `--target-extent oracle-visible --oracle-extent-identity gt`.
`-pc-mi10-oraclegt` = pc-mi10 에 같은 변경. **pc 에서 하나 더 바꾼 것**: `--nontarget-evidence surface` 제거. config 가 oracle 과 함께 이 flag 를
거절한다 (oracle 이 대신하는 ball-owned 분할에만 걸리기 때문). RB-Y1 전용 전제는 없다: oracle-visible 은 attention 을 읽지 않으므로
`--attention-source noun_target:L10H7` 이나 attention-surface 전제가 필요 없다. ATS cell (기본 `action:last:L8H2`), HSR6 규칙 · probe, 거친 층의 ball ·
권한은 base 판 그대로다. identity `gt` 는 지우는 물체를 늘 정답 target 으로 한다. **ATS 가 고른 manipulated 기하 · latch 물체는 그대로**
(t4 · t9 처럼 ATS 가 다른 bowl 을 잡으면 지우기는 정답 bowl, latch · reach 는 ATS bowl 을 따른다). 이 어긋남은 서버가
`identity_matches_gt` 로 기록한다 (call row `oracle.field.identity_matches_gt`).

## 오프라인 점검 (GPU 없음)

`benchmark/runners/oracle_offline_check.py`, 입력 `…62c0076f78b9_sl10-rec-libero9-AG3S-final-panda-v3-e0to-pc-vla…` (LIBERO spatial, episode 0).
render: `.venv-libero`, 기록된 env history 로 env 를 다시 만들어 call 프레임마다 `sim_state_at_return` (live client 가 렌더하는 시점) 에서 segmentation → code 영상.
memory: 서버 `OracleMemory` (cell 2.5 mm, 5 mm fine voxel 설정) 에 **기록된 depth · K · T_base_cam** 과 code 영상을 넣고, target-code 표본을 MuJoCo 진짜 target mesh 꼭짓점과 비교 (최근접 거리).

| episode | target (규칙) | 비교 구간 | target 표본 거리 mm (call 별 median 의 median / 최악 call 의 p90) | target 표본이 없는 call |
|---|---|---|---|---|
| t1 e0 (44→26 call) | akita_black_bowl_1 (goal 첫 인자) | 접근 · 쥐기 (call ≤ 65, 12 call) | 0.66 / 1.40 | 0 |
| t9 e0 (44 call) | akita_black_bowl_1 | 전체 (이 episode 에서 ATS 가 다른 bowl 을 옮겼고 정답 bowl 은 움직이지 않음) | 0.63 / 1.44 | 0 |

- 정답 bowl 의 표본 수는 첫 call 부터 691 (t1) · 1124 (t9) 개이고 이후 늘어난다.
- `sim_state_image` (image 시점) 로 렌더해도 같다 (0.65 / 1.40 · 0.62 / 1.21): segmentation 을 step 반환 시점에 그리는 것의 시각 차이는 측정 가능한 영향이 없다.
- **알려진 한계 (verifier 가 볼 것):** t1 에서 bowl 이 들려 옮겨지는 구간 (call ≥ 70) 에서 memory 의 target 표본에 **옛 위치의 잔류 표본** 이 쌓인다
  (median 2 → 170 mm, 표본 4.8 k → 13 k). `OracleMemory` 의 carving 은 "이 프레임의 카메라가 옛 표본 너머를 봤을 때" 만 지우는데, 팔 · 손에 가려진 표본은 지워지지 않는다.
  RB-Y1 T46e 에서 온 동작 그대로이고 접근 · 닫는 중 판정 (과제 §2 기제) 과 무관하지만, 쥔 뒤 구간의 target-free 층에는 영향을 줄 수 있다.
- 반대로 t9 처럼 정답 bowl 이 안 움직이면 끝까지 정확하다. 몇 개의 낱개 표본이 멀리 (max 24–860 mm) 있다: 움직이는 가장자리 pixel 에서 depth 와 segmentation 시점 차이.
  p90 은 1.1–1.4 mm 라 대세에 영향이 없다.
- 못 한 것: target-free 층 점유 (과제 기제: 접근 · 닫는 중 중앙값 ≤ 0.3) 와 `identity_matches_gt ≥ 0.95` 는 TSDF/ESDF (GPU) 와 ATS 가 있어야 재므로 offline 에서 재지 않았다.
  verifier 가 `target_free_check.py` 로 측정한다 (call row `oracle.field` 에 `applied` · `why` · `identity_matches_gt` · 표본 수가 있다).

## verifier 가 알아야 할 것
- 새 flag: client `--oracle-segmentation` (기본 꺼짐; 켜면 `--capture-segmentation` 이 켜져 `*_geom.npz` 에 `segmentation_geom/<cam>` int16 이 들어간다 — 용량 증가, 대신 offline 재현이 쉽다).
  서버 `--target-extent oracle-visible` · `--oracle-extent-identity {pipeline,gt}` · `--oracle-max-dist-voxels` 는 serve_safe 에 이미 있던 것이고 Panda 서버만 허용을 풀었다.
- segmentation 은 `env.step` 반환 시점, depth 는 image 시점 (camera.py 문서의 기존 규약). 위 offline 결과대로 영향은 sub-mm.
- 재생산이 필요한 산출물: 없음 (offline 산출물은 scratchpad, 저장소에 없음).
- 옛 기록과 호환: 깨지지 않음. 새 기록 키는 oracle 판에서만: call row `oracle`, episode `safe_client.oracle`, 응답 `panda/oracle`, manifest `oracle_segmentation`, config dump `final_config.oracle_visible`.
- `-lsfork` 쌍둥이는 등록하지 않았다 (등록하면 기존 `-lsfork` 판의 version record 키가 바뀌는 그룹 순서 문제가 있다). LIBERO-Safety 를 fork 응답 모델로 돌리려면 `register_lsfork` 와 dest 그룹을 먼저 손봐야 한다 — lead 결정.
- SafeLIBERO: launcher 가 거절한다. target 규칙은 env 의 `parsed_problem` 을 읽으므로 SafeLIBERO 에도 동작하지만 BDDL 로 확인하지 않았다.
- worktree 에서 `tests/benchmark` 전체를 돌리면 이 변경과 무관한 실패가 남는다: `ROOT/.venv-libero` 를 쓰는 test 들 (worktree 에 venv 없음), `test_launcher_record_constraints` · `test_parallel_gpu_launcher` · `test_panda_sl3` · `test_sl6_b5_noun_rows` (worktree 경로). `test_panda_sl5a::test_rby1_golden_identity` 는 main 에서도 실패한다 (이미 있던 것). 이 변경으로 새로 생긴 실패는 없다 (registry test 3개는 위처럼 SL12 두 판을 제외하도록 고쳤다).

## 내가 기대하는 결과
(verifier 는 측정 전에 읽지 않는다) 접근 · 닫는 중에는 정답 bowl 부피의 target-free 점유가 크게 떨어지고, 정답 identity 비율은 t4 · t9 처럼 ATS 가 다른 bowl 을 잡는 episode 에서 낮다
(그 비율은 지우기가 아니라 ATS 의 latch · 접근 물체를 따른다). 쥔 뒤 구간은 위 잔류 표본 때문에 더 복잡할 수 있다.
