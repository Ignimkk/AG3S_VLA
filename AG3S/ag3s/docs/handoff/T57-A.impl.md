## 무엇을 했나 (평이한 요약 먼저)

서버에 기본 off flag 셋을 더했다. (1) `--attention-source SPEC` 은 AG3S 에 들어가는 attention 의 셀을 고른다 —
`noun_target:L10H7` 은 prompt 의 target 명사 token 행 (prefix pass, raw σ0 k1) 으로 T57 단계 1 의 N 이고,
`action:mean:L10H7` 은 T61 선택 (구현만). 명사를 못 찾은 요청은 attention 을 비우고 (합성하지 않는다) 사유를 남긴다.
(2) `--task-gate` 는 latch 가 **HELD** 인데 T55 prereg 명사 probe (target 명사 token 의 layer-5 V · logistic ·
τ 0.3 · p 1 · noun_ok 필요) 가 통과하지 않으면 그 청크에 `task_not_ready` 사유를 더해 기존 HOLD 경로로 보류한다.
HELD 가 아니면 아무것도 막지 않는다. (3) `--task-gate-shadow` 는 같은 값을 요청마다 계산해 기록만 한다.
두 단계는 같은 명사 lookup (`t49_noun_query_extract.lookup`) 과 같은 prefix pass 의 gather 를 쓴다. flag 를 안
주면 출력이 base 와 byte 동일하다 (CPU harness, 아래).

## 설계 (왜 이렇게)

1. **SPEC 하나로 일반화, 기본 경로는 손대지 않는다.** `AttentionPolicy.infer` 는 flag 가 없으면 T57 전 코드
   (`_attention_and_feature`, 모듈 상수 `_DENOISE_STEP/_AGG/_LAYER/_HEAD`) 를 그대로 탄다
   (`attention_policy.py:142-156`). flag 가 있을 때만 `_infer_extended` (`:159-226`) 로 간다 — 두 경로가 갈라져
   있어 기본 경로의 bit 동일성이 구조적으로 보장된다. SPEC 문법 · 검증은 `attention_source.py:90-151`
   (`action:<mean|first|last>:L<l>H<h>` · `noun_target:L<l>H<h>`, 18 layer × 8 head 밖 · 모르는 pooling 거절,
   action 은 denoise 0 만).
2. **명사 = policy 에 실제로 들어간 prompt 의 명사** (T55 정의). prompt 의 과일 단어가 정확히 하나일 때만
   (`t48_hsr_core.prompt_template` 의 regex) 그 명사이고, 그 piece 를 policy 의 input transform 이 만든
   `tokenized_prompt` 에서 `t49_noun_query_extract.lookup` 으로 찾는다 (`attention_source.py:154-224`) —
   T53 / T55 `feature_frame` 과 같은 호출이라 같은 행 (`basket` 도 정확히 하나, token 0 = `<bos>`; 아니면
   `noun_ok = False`, 추측하지 않는다). request 에 prompt 가 없으면 `--default-prompt` 를 쓴다.
3. **같은 prefix pass 에서 gather.**
   - 단계 1 (noun source): `JaxPrefixBackend._noun_pass` (`attention_source.py:359-367`) 가 `AttentionSampler._prefix`
     와 같은 prefix pass 를 돌리고 확률 텐서에서 행을 `t49_noun_query_core.slice_probs` (T49 추출과 같은 함수) 로
     jit 안에서 잘라 (L10, H7) 의 image 열 768 개만 꺼낸다 (`prefix_noun_impl`, `:314-332`). 같은 pass 의 KV 로
     subtask kv_L4 feature 도 만든다 (`sampler._jit_kv_feature`). action query 의 suffix loop 은 돌지 않는다.
   - 단계 2 (probe): V 행은 **그 요청의 prefix pass KV cache** 에서 꺼낸다 (`v_rows_impl`, `:335-342` =
     `t53_extract.noun_token_impl` 의 V gather 한 layer). action source (gate arm) 에서는 sampler 자신의
     `_jit_prefix` cache 를 쓴다 — `AttentionSampler._sample(kv_hook=)` (`pi05_attention.py:180-193`, 기본 None
     = 아무것도 안 함) 로 받아 두 번째 prefix pass 가 없고 서빙 attention 은 기본 경로와 같은 executable 이 만든다.
   - probe 적용은 policy 쪽 (`AttentionPolicy`, HSR kv_L4 와 같은 자리): `result["task_probe"] = {p, ok, noun_ok,
     noun, error, feature, probe_md5, token_index, feature_sha1}` (`attention_policy.py:207-219`). p =
     `t50_core.LogReg.proba(x)[0, 1]` (`t55_study.score_test` 와 같은 식, `attention_source.py:268-271`).
4. **gate 위치 (사용자 판정 6 그대로).** `SafePolicy._verdict` 에서 `_reasons` → (`--hold-follow-to` 이면)
   `_follow_to` 뒤, `wire.gate_decision` 직전 (`safe_policy.py:1656-1660`). latch 상태는 `_scene_fn` 의
   `_advance_grasp` · `_run_latch` 이 끝난 이번 요청의 최종 phase (기록 `grasp.state` 와 같은 값, T55 의
   `phase` 열 정의와 같다). `_task_gate` (`:1713-1766`):
   `held = phase is HELD`, `probe_pass = ok ∧ noun_ok ∧ p 유한 ∧ p ≥ τ`, `task_ready = held ∧ probe_pass`,
   `applied = (mode == on) ∧ held ∧ ¬probe_pass` → `task_not_ready` (evidence `probe_p` · `tau` · `noun_ok` ·
   `latch_state` · `noun`). probe 가 없거나 깨지면 통과가 아니다 (fail closed). 다른 사유는 건드리지 않는다.
   `wire.REASON_KINDS` / `GATE_DEFAULT` 에 `task_not_ready: hold` (`wire.py:148, :361, :387`) — 이 kind 를 모르는
   옛 client 도 HOLD 한다 (fail closed).
5. **HOLD 중에도 추론은 계속된다.** gate 는 판정 사유만 더한다 — `SafePolicy.infer` 는 요청마다 정책 · prefix ·
   probe · latch 를 새 관측으로 다시 돈다 (바뀐 곳 없음). 요청마다 `task_gate` 기록 (아래) 의 `probe_p` ·
   `feature_sha1` 이 새로 계산됐음을 보인다 (테스트 7).
6. **T43 Z6 (`--hold-follow-to`, T54c C1a profile 에서 3) 와의 상호작용.** follow_to 판정은 gate 와 무관하게
   먼저 그대로 계산된다. 그 청크를 gate 가 HOLD 하면 실제로 따르지 않았으므로 `_follow_to` 가 올린 streak 만
   되돌린다 (`safe_policy.py:1752-1758`, 기록 `verdict.follow_to.held_by = task_not_ready`). 이것이 없으면 HOLD 된
   청크가 한도 (3) 를 소모해 probe 회복 뒤의 follow_to 를 막는다.
7. **씬이 없는 청크** (refiner 가 못 돈 경우): 판정은 원래 사유 없이 HOLD 다 (wire 모양 불변). gate 는 기록용
   사유 목록에만 `task_not_ready` (`carried_on_wire: False`) 를 더하고 기록에 `scene: False` 를 남긴다.
8. **shadow** = 같은 `_task_gate` 를 돌리되 `applied` 는 언제나 False (판정 불변). gate 와 shadow 를 같이 줄 수는
   없다 (argparse mutually exclusive — gate 가 shadow 의 기록을 모두 남긴다).

  따로 세야 한다 (T57 단계 2 의 보고 요구 — 이 patch 는 분석 도구를 바꾸지 않았다).

## 알려진 한계

- **map dtype**: 서버의 noun map 은 float32 raw 다. T54c/T54 의 N 재생은 float16 으로 저장된 map 을 썼다 → 정확
  parity 는 float16 반올림까지만 기대할 수 있다 (replay stage 가 f16 · f32 두 입력으로 그 차이가 AG3S 결과를
  바꾸는지 따로 잰다).
- **noun source 의 subtask label**: kv_L4 feature 가 noun pass (다른 executable) 의 KV 에서 나온다. 같은 연산이지만
  XLA fusion 차이로 bit 단위로 같다는 보장은 없다 — probe stage 가 차와 label argmax 일치를 잰다. noun source 는
  action query suffix loop 을 돌리지 않으므로 action map 은 기록되지 않는다.
- **probe p 의 1-ulp 차**: 한 행 계산과 batch matmul (offline) 의 BLAS 합 순서 차 (CPU 실측 상대 ~1e-15). τ 판정은
  test 행에서 같았다.
- **state dtype**: T55 feature 는 state 를 float32 로 바꿔 input transform 에 넣었다 (`FeatureExtractor.inputs`).
  서버는 client 가 보낸 dtype 그대로다 — discrete state token 의 경계값에서 prompt token 이 달라질 수 있다 (probe
  stage 는 T55 와 같이 float32 로 넣는다).
- **명사 = prompt 의 과일 단어 하나.** 과일이 둘 이상이거나 다른 명사 (예: crate) 인 prompt 는 `noun_ok = False` →
  noun source 는 attention 없음, gate 는 HELD 이면 HOLD. 16D 과제 prompt 는 과일 하나 + basket 이다.
- **wrong-object 상황 만들기 (dev 확인 2)** 는 이 patch 에 없다 (policy prompt 와 probe 명사를 분리하는 디버그
  flag 를 넣지 않았다 — 배포 경로가 아니다). lead 가 방법을 정하면 별도로 넣는다.
- **follow_to streak 되돌리기** (설계 6) 는 gate on 에서만 일어난다. 그 밖의 follow_to 판정 · 기록은 그대로다.
- HELD 의 false negative (T55b #48 · #49) 는 이 gate 가 되돌리지 않는다 (HELD 가 아니면 작동하지 않는다).
- 분석 도구 (`analyze_cl` · `agg_cl` · `t60_termination`) 의 사유별 HOLD 집계는 바꾸지 않았다.
