## 무엇을 했나 (평이한 요약 먼저)

**목적.** DT-02 extent block 은 같은 identity 에서 target 범위 처리만 바꾼 arm 들을 비교한다 (`ball` · `ball_owned` · `ball_owned`+F1 · **oracle**).
oracle 은 "카메라에 실제로 보인 target 표면에서 온 seed 만 지운다" 는 **진단 기준**이다. 제안 extent 가 이상적인 경계에 얼마나 가까운지를 closed loop 에서 잰다.
이 STEP 은 그 arm 을 server · client · wire 에 붙였다. **기본은 off 이고, off 면 예전과 비트로 같다.**

**이전 대비.**

| | 이전 (V11AB = C0 `ball` · C1a `ball_owned` · +F1/F2) | `--target-extent oracle-visible` (새, 기본 off) |
|---|---|---|

  - `pipeline` = AG3S manipulated 기하가 놓인 물체 (DX-01 조건 B: identity 는 다른 arm 과 같고 extent 만 GT).
  - `gt` = 늘 GT target (identity 와 extent 둘 다 GT 인 미세 계층 상한).

  - **AG3S 전체의 identity 를 GT 로 바꾸는 것 (공 · 창 · 권한 · latch 까지) 은 하지 않았다** — 판정 1.

## 2. oracle 의 정의 — 고른 방법과 근거

### code 표 (`AG3S/ag3s/runtime/oracle_segmentation.py:57-97`)

| code | 무엇 |
|---:|---|
| 0 | 안 맞음 · **로봇** (근거로 쓰지 않는다 — 로봇은 self-filter · depth mask 가 이미 뺀다) |
| 1 | episode 의 GT target |
| 2 | 정적 — table · crate · 바닥 · 벽 |
| 3 … | target 이 아닌 잡을 물체 (과일마다 하나). 자식 body 는 root body 의 code |

### memory (`OracleMemory`, `oracle_segmentation.py:142-363`) — 왜 이 요청의 pixel 만으로 안 되나

TSDF 는 episode 동안 누적된다 (`time_decay = 1`). grasp 직전에는 손이 target 을 가려 그 요청에 보이는 target pixel 이 준다.
그런데 앞 요청들이 본 target 면의 seed 는 TSDF 에 남는다. 그래서 memory 도 같은 규약으로 모은다.

| 단계 | 규칙 |
|---|---|
| 표면 표본 | 유효 depth · code ≠ 0 pixel 을 base 로 올린 점, 2.5 mm 칸에 하나 — 새 관측이 덮는다 |
| ROI | 잡을 물체 표본 AABB + `2·max_dist + vs` (= 65 mm) 밖은 담지 않는다 (분류를 못 바꾼다) |
| carving | 이 요청의 카메라가 옛 표본 **너머** 를 보면 (투영 pixel 주변 5×5 의 가장 가까운 유효 depth > 표본 + 10 mm) 지운다 — 물체가 움직였다. 5×5 최소는 실루엣 가장자리 pixel 이 물체를 비껴 뒤 table 을 맞히는 경우 때문 (합성 rig 에서 이것 없이는 같은 장면 재관측에 78 표본이 지워졌다) |
| truncation 띠 | 잡을 물체 pixel (2 pixel 마다) 의 광선을 따라 보인 면 뒤 30 mm (= 미세 TSDF truncation) 까지 지나간 5 mm 칸과, 그 칸을 지나간 물체 code 의 bit mask. 지우지 않는다 |
| reset | episode 마다 (`AG3S.reset`) |

### 분할 (`AG3S/ag3s/fields/curobo_builder.py:616-668`, `oracle_visible_split`)

후보 = 그 물체 표본에서 `oracle_max_dist_voxels` (6 = 30 mm) 안의 voxel (`oracle_candidates`, `:594-613`). seed 마다:

| 길 | 조건 | 무엇을 잡나 |
|---|---|---|
| 표면 | `d_t < d_o` (`d_t` = 그 물체 표본, `d_o` = 다른 표본) ∧ `z ≥ z_floor` | 보인 표면의 seed |
| 띠 | 그 칸의 띠 mask 가 **그 물체 bit 하나뿐** ∧ `d_o > 1 voxel` (5 mm) ∧ `z ≥ z_floor` | 보인 면 뒤 truncation 띠의 경계 = 물체 밑 · 안쪽의 그림자 seed |
| 그 밖 | | 보존 — 이웃 · table · crate, 두 물체 띠가 겹친 칸, 동률 |

- `z_floor` = 공의 `z_min` (지지면 평면 + 1 voxel; `ball` · `ball_owned` 와 같은 지지면 보호).
- 부호 교정 = 지운 seed ∪ 표면 길의 non-seed (그 물체 안쪽). 띠 길은 non-seed 부호를 바꾸지 않는다 (띠가 이웃 안쪽에 닿을 수 있어서).
- **왜 띠 길이 필요했나 (실측).** 표면 길만으로 smoke 를 돌리자 C1a_ep54_s541 seq 16 에서 off 가 지우는 seed 425 개를 oracle 이 남겼다. 충돌 행은 61 (off 29).
  - 그 seed 는 GT target hull 밖 중앙 10 mm, table 위 약 7 mm 였다. 그중 196 개는 어떤 표본에서도 10 mm 넘게 떨어져 있었다.
  - 이 요청의 카메라로 투영해 보니 head 카메라는 그 자리를 **손 (로봇 pixel, TSDF 에서 지움) 뒤로** 봤다. 즉 앞 요청들의 target 광선이 만든 seed 다 → 띠도 누적해야 한다.
  - 띠 칸을 2.5 mm 로 둔 v1 은 design17 266 행이었다. head 카메라 광선 간격 (≈ 1.5 mm/px × stride 2) 이 칸보다 커서 칸이 비었다 → 5 mm 로 바꾼 v2 가 160 행이다 (§5).
  - 진단 스크립트: `p/diag_kept.py`.

### identity (`oracle_segmentation.py:365-401`, `oracle_evidence`)

- `pipeline`: manipulated 기하 점마다 10 mm (fusion voxel) 안 가장 가까운 표본의 code → 물체 code 다수결 ≥ ½.
- `gt`: code 1.
- 정해지지 않으면 (segmentation 없음 · memory 빔 · 다수 없음 · 표본 없음) 그 frame 은 **추정 범위 (`--target-exclusion`) 로 짓고** 이유를 남긴다.

## 판정이 필요한 것

1. **oracle identity 를 AG3S 전체에 넣을지 (task §3, DX-01 조건 A).** 이번에는 oracle extent 의 물체 선택 (`--oracle-extent-identity gt`) 과 `identity_matches_gt` 기록까지만 넣었다. AG3S 의 manipulated identity 를 GT 로 바꾸는 것 (조건 A: GT identity × 제안 extent) 은 값싸지 않아 하지 않았다.
   - identity 는 `TargetConfirm` (adoption · freeze · latch · anchor) → exclusion gate (`pipeline.py:_exclusion_gate`, 최대 개도 · 목적지 검사) → 공 · 창 · `manipulated_link_margin` · 다음 frame guard · grasp latch · attach 까지 흐른다. 바꾼 기하는 gate 불변식 (bounding geometry · 개도) 을 다시 증명해야 한다.
   - 최소안: `_exclusion_gate` 뒤에서 `manipulated_geometry` 만 `exclusion_e2.choose_identity` 의 `gt` 규칙 (pipeline ≥ 80 % → nearest cluster ≥ 80 % → GT 라벨 cloud 점) 으로 바꾼다. GT 라벨은 이 STEP 의 memory 로 cloud 점에 붙인다. target 이 없는 frame 에 target 을 만들지는 않는다.
   - 이것을 할지, 그리고 gate 를 다시 통과시킬지 정해 주면 한 STEP 으로 구현한다.
2. **지지면 층.** off · F1GT 는 공의 `z_min` (평면 + 1 voxel) 위를 다 지운다. 그래서 TSDF 의 table 영교차 (평면 위 ≈ 7 mm) 를 target 밑에서 지운다.
   - oracle 은 그것을 table 로 보고 남긴다 — task 의 "지지면은 지우지 않는다" 대로다.
   - smoke 에서 이 층의 몫은 −7 / −15 행 (ORV_S) 으로 작다. 그래도 oracle arm 이 다른 arm 과 같은 지지면 처리 (공 `z_min` 위 지지면 층 제거) 를 따를지 정해야 한다. 그러면 option 하나를 더한다.
3. **F1GT 는 visible-target 상한이 아니다.** 행 감소의 일부는 공 안 이웃 과일 seed 제거에서 온다 (지운 seed 중 이웃 ≤ 5 mm 1,824 / 2,221 대 oracle 1 / 6).
   - CL4 / DT-02 에서 "제안 extent 가 이상 경계에 얼마나 가까운가" 의 기준을 oracle 로 둘지 F1GT 로 둘지는 lead / 사용자 판단이다. 이 smoke 는 둘이 다르다는 것만 보였다.
4. **oracle 의 정의 두 가지 (설계 판단).**
   - (a) 띠 길: 물체 pixel 광선의 보인 면 뒤 30 mm 를 누적, 그 물체 bit 만인 5 mm 칸, 다른 표본 5 mm 보호.
   - (b) 띠 길은 non-seed 의 부호를 바꾸지 않는다.
   - 둘 다 이웃 보호 쪽으로 기울인 선택이다. 띠 깊이 = 미세 TSDF truncation 이고 칸 = 미세 voxel 이다. 표면 길만이면 그림자 seed 가 남아 ep54 seq 16 이 off 보다 나빠졌다 (61 대 29 행).
5. **거친 target-free 계층 (`--target-free-coarse`) 과 함께 켜면** 거친 계층은 oracle 이 아니라 `--target-exclusion` 그대로다 (시작 WARNING). C1a 묶음은 coarse off 라 CL4 에는 영향이 없다.
6. **지연 ~200 ms / chunk** (CPU, 부하 18). 진단 arm 이라 그대로 두었다. CL4 의 시간 지표 (완료 시간 · stop) 를 oracle arm 과 비교할 때 이 차이를 감안해야 한다.

- **off bit-identical:** 차이 0. CL3 기록 replay 는 이 STEP 전과 같고 (1618/1630, 나머지 12 는 HEAD 와 동일), GPU 층은 `torch.equal` 일 것이다.
- **offline (같은 harness):** oracle 충돌 행은 design17 ≈ 160 · held-out ≈ 216 일 것이다 (off 601 / 887, F1GT 72 / 113). HOLD 0 행은 7/14 · 5/12 다. 지운 seed 중 이웃 ≤ 5 mm 는 GT identity 에서 한 자리 수일 것이다.
- **closed loop (재지 않았다):**
  - oracle arm 의 `applied` 비율은 pre-grasp 에서 ~100 % 일 것이다. `no_target_free_layer` 는 attach 뒤 · target 없는 frame 이다.
  - grasp 직전 HOLD 는 C1a 보다 크게 줄 것이다. 다만 이웃이 닿아 있는 배치 (ep110 · ep3 · ep123) 에서는 이웃 seed 가 남아 C1a+F1 보다 나쁜 chunk 가 몇 개 나올 수 있다.
  - task success 는 C1a 이상, F1GT 를 흉내 낸 arm 보다는 낮을 수 있다.
- **identity:** CL3 류 18 쌍에서 `identity_matches_gt = False` frame 은 소수 (ep3 계열) 일 것이다. 그 frame 에서 `pipeline` oracle 은 이웃을 지운다 — `gt` 와의 차이가 identity 오류의 몫이다.
