## 무엇을 했나 (평이한 요약 먼저)

기록된 **실행 action** 만으로 MuJoCo 를 처음부터 다시 돌리는 재시뮬 driver 를 완성했다. 매 frame qpos 를 덮어쓰지 않는다. 여기에 두 개입 hook 을 넣었다: (1) 닫기 전에 target 을 치우는 empty grasp, (2) 쥔 뒤 물체를 손에서 떼는 slip.
재시뮬의 실행 feedback 으로 `grasp_latch` 를 offline 으로 돌린다. 물리 predicate 는 P_grasp · P_task · 지속 `K` · 4 상태다. 재시뮬 image 와 instruction 변경 prompt 의 kv_L4 · 명사 token feature 는 T53 producer 를 그대로 써서 GPU 로 뽑는다. dev 단계에서 episode-fold CV 로 설정을 고정하고 `T55.prereg.json` 을 쓴다. test 단계는 prereg 를 읽기만 하면서 오류 · 지연 · paired 차이 · bootstrap 을 낸다.

**E0 feasibility (먼저 확인함):**
- T53 record 는 **bit 단위로 일치한다** (ep1804: qpos · qvel · state · image 3 camera · measured · `applied_gripper` · feedback 75/75 · 기록된 latch 상태 75/75 전부 차이 0).
- dev record (T47 · T51 calibration) 는 **정확히 일치하지 않는다.** frame 0 은 일치하지만, 기록된 action 이 float32 라서 frame 1 부터 약 2e-8 rad 이 나고 grasp 무렵부터 발산한다.
- qpos 덮어쓰기로 대신하지 않았다. dev 개입 재시뮬은 `--accept-nonparity` (lead 결정) 없이는 거부한다.

### 정의 (구현이 고정한 것 · task 의 사전 고정은 바꾸지 않음)

| 항목 | 정의 |
|---|---|
| P_grasp / P_task | used arm 의 두 finger body 가 그 과일과 접촉하고, 그 과일이 table · crate 와 비접촉 (`classify` 의 `held`, 과일 4 개 전부). P_task = 그 과일이 prompt 의 명사. P_task ⊂ P_grasp |
| 4 상태 | `target_held` (P_task) > `wrong_object` (P_grasp ∧ ¬P_task) > `placed` (¬P_grasp ∧ 명사 과일이 crate 안 · 손에 없음) > `empty` |
| 지속 K | causal: False 에서 시작해 반대 값이 K frame 연속이면 뒤집힘 (onset 은 K 번째 frame, release 도 K). val frame (dataset, stride 6) 에는 적용하지 않음 |
| 조건 window | natural · instruction = 모든 frame, empty · slip = `window_start` (= 개입 frame + 1) 부터 |
| instruction 의 strong rule | E0 의 latch trace 그대로 (입력이 실행 feedback 과 기록된 perception — prompt 교체를 반영하지 않는다는 가정을 결과에 같이 적을 것) |
| feature flag | HSR: `kv_L4_v1` p(place) ≥ τ (또는 argmax = place); 명사: probe p ≥ τ, `noun_ok` 아닌 frame 은 False. 둘 다 causal p frame AND (`feature_persist`) |
| task_ready | `HELD ∧ flag` (`combine`). attach / detach / phase 배열은 바꾸지 않음 (test 로 고정) |
| K rule (dev) | dev E0 마다 excess = max(0, P_grasp onset 수 − strong rule closing 시도 수), 합이 최소인 가장 작은 K (후보 1 2 3, `--K` 로 덮으면 override 로 기록) |
| 명사 probe | feature = target token 의 `noun_v[layer]` (256) 또는 `noun_hidden_final` (2048); 표준화 + L2 binary logistic (`t50_core.fit_logreg`, K=2); label = persistent P_task (val: place ∧ orig); 학습 행 = natural · instruction · val 전부 + empty · slip 의 window frame. GroupKFold(min(5, group 수)) |
| 결합 선택 | dev re-sim trace 전체 (조건 pooled window, P_task) 에서 Δ false-reject rate ≤ 0.10, Δ 평균 paired 지연 ≤ 2 frame, Δ 미검출 onset ≤ 0 을 만족하는 격자점 중 false pass 최소 (동률: Δfr 작음 → p 작음 → 격자 순). 없으면 `feasible: false` + 위반 합 최소. **허용폭 3 개는 구현자 기본값** — CLI 로 바꾸고 lead / 사용자가 확정 |
| latch mode | dev = `oracle` (dev record 에는 server 기록이 없음), test 기본 = `record` (기록된 perception), `oracle` 은 secondary 로 함께 채점 |
| bootstrap | episode block (group 단위 복원 추출, B 10000, seed 5507, percentile 95 %), moving block 5 frame (trace 안, rate 만), frame McNemar exact (참고) |

### 남은 결정 · 주의 (대체)

1. **ESDF backend.** 기본 `legacy` (CPU). 서빙은 cuRobo 였다. ep1804 E0 에서 legacy 가 grasp 기록을 75/75 재현했다 (위 표). 다른 episode 에서 차이가 나면 그 차이는 `serving_parity` 에 숫자로 나온다. `server` backend 로 바꿀지는 lead 가 정한다.
2. **instruction 조건의 재-grounding 은 구현 가능했다** (보고할 불가능 사유 없음). 다만 결과는 GPU attention (바뀐 prompt) 을 뽑은 뒤에만 나온다.
3. **요청 시각 · reference chunk** 는 위 "정의" 표의 근사다 (sim 시각, 개입 뒤에도 기록된 reference chunk). 둘 다 latch 판단 경로에는 들어가지 않는 것으로 보았지만 (요청 안 시각 차이 0, chunk 는 실행 창에만), 가정으로 결과에 같이 적을 것.
4. `record` mode 는 test 에만 있다 (dev record 에는 서버 기록이 없다). dev 의 보조 mode 는 `oracle` 뿐이다.
5. `t54_replay.py` (다른 세션 소유, 미 commit) 의 `c1a_build_kwargs` · `server_argv` 를 쓴다. 그 파일이 바뀌면 server 구성이 바뀔 수 있다 — md5 를 meta 에 남긴다.

### 내가 기대하는 결과 (verifier 는 측정 전에 읽지 않는다)

- test E0 의 `reground` latch 는 대부분의 episode 에서 기록과 같을 것이다 (ep1804 처럼). attention 재추출 차이 (argmax ≈ 0.996) 로 몇 요청이 어긋날 수 있다.
- empty 에서 reground 는 `held` 에 가지 않을 것이다 (feedback 이 빈손 닫힘). slip 에서는 revoke 까지 1–2 frame `held` 가 남을 것이다.
- instruction 조건에서 reground latch 는 원래 target 을 쥔 frame 의 `held` 를 많이 잃을 것이다 (AG3S 가 다른 과일을 grounding → reach 거절). 그러면 strong rule 단독의 instruction false pass 가 `record` mode 보다 작게 나올 것이다.
