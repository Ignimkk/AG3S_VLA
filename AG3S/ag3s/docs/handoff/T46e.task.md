## 왜 지금 이것인가
Ablation DT-02 의 extent block 은 같은 identity 에서 extent 처리만 바꾼 arm 들로 이루어진다:
| arm | extent | 상태 |
|---|---|---|
| ball | V11AB (C0) 의 `ball` exclusion | 있음 |
| ball_owned | C1a | 있음 |
| **제안** | ball_owned + F1 (`--nontarget-evidence surface`) | 있음 (T46) |
| **visible-target oracle** | 시뮬레이터의 GT 로 **카메라에 실제 보인 target 표면 점만** target 으로 지운다 (extent 상한) | **없음 → 이 STEP** |
oracle 은 "제안 extent 가 이상적인 경계에 얼마나 가까운가" 를 closed-loop 에서 재는 기준이다 (L4: offline GT 상한 113 행 대 F1 401 행). 그리고 **identity 를 GT 로 고정** 하는 경로가 있어야 extent 와 identity 효과를 분리할 수 있다 (DX-01 조건 A 의 oracle identity).

## A13 — 구현 (implementer, Opus)
1. **먼저 audit:** 이미 있는 GT 경로를 찾아 재사용한다 — T44 E2 의 `gt` · `gt_label` identity (offline harness), D-TF / V-T46 의 GT hull 라벨, client 의 MuJoCo segmentation 렌더 가능 여부 (`integration/rby1/bringup/pi05_infer.py`, `--record-frames`). closed-loop 에서 쓸 수 있는 최소 경로를 정하고 근거 (`파일:줄`) 를 impl.md 에.
2. **oracle extent (기본 off):** 매 frame 카메라별 GT target segmentation (target geom id 의 visible pixel) 을 client 가 server 로 보내고 (wire 확장 — 기존 client 와 호환, 키 없으면 off), server 는 그 pixel 의 depth 점에서 온 seed 만 target 으로 지운다 (ball / ownership 판정 대신). 이웃 과일 · 지지면 · 로봇은 지우지 않는다. 예: `--target-extent {ball_owned(기본),oracle_visible}` 또는 동등한 config.
3. **oracle identity (가능하면 같은 경로로):** target identity 를 GT 로 고정하는 option (attention 은 계속 계산 · 기록하되 target 선택만 GT). 이미 있는 `gt_label` 류가 있으면 그것을 closed-loop 에 연결.
4. 기존 arm (ball · ball_owned · F1 · W1 · permission strict) 과 조합 가능해야 한다. off 에서 bit-identical (기록 chunk replay).
5. Tests: off bit-identical, 합성 rig 에서 oracle 이 target visible 점만 지우고 이웃 · 지지면은 남김, wire 호환 (구 client), config/CLI 왕복, 전체 pytest (GPU 는 `( flock -w 600 9 || exit 13; … ) 9>/tmp/ag3s-vla-gpu-validation.lock`).
6. smoke: 1 run closed-loop 은 하지 않는다 (verifier 몫). offline replay 로 oracle 이 D-TF 의 F1GT 상한과 같은 방향인지 (충돌 행) 확인만.

### T46e-D — 8 chunk · 지지면 층 원인 진단 (verifier, Opus, CPU offline, worktree `agent-a770cbc1ab3162e54`)
측정만 한다 (코드 · 해석 쓰지 않음, 분류 규칙은 측정 전에 verify.json 에 적고 고정).
1. 대상: 위 8 chunk. 각 chunk 의 oracle 충돌 행을 일으킨 구 · voxel 을 찾아, 그 voxel 의 출처 seed 를 GT 로 분류: 이웃 과일 · crate · 지지면 (table) · target · 로봇 · 그 밖. 그리고 그 voxel 위치에서 **실제 MuJoCo geom** (기록 qpos 의 장면) 까지의 거리 — 실제 표면이 있으면 "정상 장애물 보존", 없으면 "표현 · memory 오류" 후보.
2. 오류 후보는 하위 원인을 숫자로: oracle memory 의 frame 출처 (몇 frame 전 관측인가, HOLD 요청 포함 여부), back-projection depth 대 GT depth 차, 그림자 (보인 면 뒤 띠) seed, `pose_error_mm`, `applied = False` 여부, `identity_matches_gt`.
3. 같은 8 chunk 에서 off · F1 · F1GT 는 왜 0 행인가 — 같은 voxel 을 지웠는가 (지운 seed 의 GT 분류).
4. **B2 (지지면 층):** 162 chunk 전체에서 off · F1GT 가 지우고 oracle 이 남기는 지지면 층 (`z_min` 위 10 mm) 의 voxel 이 실제 table 표면 (MuJoCo) 에서 얼마나 떨어져 있는가 (TSDF zero crossing 대 실제 평면), 그 voxel 이 만든 충돌 행 수, 그 행에서 로봇 구의 실제 table 까지 거리. ORV_S 의 이웃 근접 삭제 3,627 seed 가 어떤 GT class 인지.
5. figure: 8 chunk 중 대표 2 개의 실제 씬 (target · 이웃 · 문제 voxel · 로봇 구) + 분류 막대 그래프 + 표, `figures/t46/t46e-d-*` (+ `.json`). 산출 `T46e-D.verify.json` (worktree 의 handoff).
