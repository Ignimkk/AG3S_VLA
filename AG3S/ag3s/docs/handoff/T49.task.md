## 왜 지금 이것인가

T47 은 논문의 label-free 기준 (attention sum + spatial entropy) 을 **action (suffix) token query** 에 적용했다. 결과는 실패였다. 선택된 공통 top-3 (L4H1 · L2H0 · L14H5) 는 held-out target mass 0.012–0.017, 3D `on_target` 0/30 이었다.
그 이유로 두 가지가 의심된다 (T47b #5 가 정식으로 잰다): 고정 patch sink, 그리고 넓게 퍼졌지만 한 덩어리인 map.

논문의 원래 설정은 **text query** 이다. 논문 부록 D.4 는 여러 물체를 다룰 때 **명사 token** 마다 map 을 따로 만든다. 우리도 같은 일을 할 수 있다는 것이 확인됐다 (조사, 2026-10-12):

| 사실 | 근거 |
|---|---|
| pi0.5 prefix 는 **완전 bidirectional** 이다 — text 행이 image 열을 본다 | `third_party/openpi/src/openpi/models/pi0.py:20-45, 108-139` (image · text 모두 `ar_mask=False`) |
| prompt 형식은 `"Task: {prompt}, State: {16 ints};\nAction: "` 이고 state 는 task 뒤에 온다 | `models/tokenizer.py:22-29`, `training/config.py:130-142` |
| `▁apple · ▁banana · ▁pear · ▁orange · ▁basket` 은 **단일 SentencePiece** 이다 | tokenizer `…/cache/rby1/openpi/big_vision/paligemma_tokenizer.model` |
| prefix 배치: `[cam_high 0:256 · left_wrist 256:512 · right_wrist 512:768 · text 768:968]`. 명사의 query 행 = `768 + text_idx` | `policy_record.py:43-51` |
| repo 의 openpi patch 가 attention probs 를 반환한다. 지금 `_prefix` 는 그 probs 를 **버린다** | `gemma.py:164,254,299,317,361,394,431`; `pi05_attention.py:95-105` (`[1]` 만 취함) |
| denoise · noise seed 가 필요 없다 → **결정적** 이고 prefix pass 1 회로 끝난다 | prefix 에는 suffix 가 없다 |

action query 와 다른 점:
- action query 는 policy 가 "어디로 움직이려 하는가" 를 본다. 잡은 뒤 basket 으로 옮겨갈 수 있다.
- 명사 query 는 "이 단어가 무엇을 가리키는가" 를 본다. phase 와 무관하게 이름 붙은 물체에 머물러야 한다.
- **target 과 목적지를 서로 다른 단어로 따로 얻는다.** 지금은 목적지를 규칙 (잡을 수 없음 + 3 frame 우위) 으로만 판정한다.

```
RGB ×3 + prompt + state → VLA prefix (frozen, bidirectional) ─┬─ 행 768+idx(target 명사) → image 768 열 → target map  (3 cam × 16×16)
                                                              └─ 행 768+idx("basket")    → image 768 열 → 목적지 map
   → [T47 평가: 2D class mass · lift · IoU] → [T47 e2e: lifting → grounding → on_target · identity_correct]
```

## 사전 고정 (결과 보기 전)

| 항목 | **primary** | secondary / exploratory |
|---|---|---|
| query 행 | prompt 의 target 과일 명사 1 token (target map) · `basket` 1 token (목적지 map) | — |
| cell 선택 | **GT 기반**: selection record (`long`, `t2`, `ep1807`) 에서 target map 의 **lift 평균** 으로 18×8 cell 의 순위를 매기고 top-3 를 σ=1 raw 합으로 쓴다 | **secondary**: 같은 명사 행에 T47 의 label-free 절차 (S_cam τ Kneedle + spatial entropy + selection frequency, L0·L1 제외, k=3) 를 적용한다. 논문과 같은 *text query* 에서는 label-free 가 통하는지를 본다 |
| 목적지 map cell | target 과 **같은 방식으로 따로** 고른다 (crate coverage 기준 lift) | 같은 cell 을 쓰는 변형 |
| 평가 | held-out 4 record (same-scene `headfix`·`ep1800` / new-scene `ep1850`·`ep1900`) — **pilot** | k = 1..5, σ = 0 |
| 비교 기준 | **L8H2 (action query, 서빙)** · T47 oracle top-3 (action) | head-average (명사 행) |

- frame 이 아니라 record (episode) 단위로 판단한다.
- **사용 불가 layer 기준 (lead, T49.impl.md 확인 후 · 결과 전 고정):** 명사 행의 image 768 열 mass 의 **record 통합 median < 0.01** 인 layer 는 "image 를 거의 보지 않음" 으로 표시한다 (`--min-image-mass 0.01`).
  primary GT top-3 선택에서는 이 기준으로 layer 를 **제외하지 않는다** — 표시만 한다. 제외 여부는 결과를 본 뒤가 아니라 지금 정한 대로다.
- verifier 는 먼저 smoke (`--records ep1850 --no-swaps`) 를 돌리고 본 실행으로 넘어간다 (T49.impl.md).
- "basket" 의 GT body 는 `crate` 다 (`attention_report.py:64-70` alias). 모든 16D prompt 가 "basket" 이라 부른다.

4. **분리 지표.** frame 마다 다음을 계산한다.
   - target map 의 raw argmax 가 target body 위에 있는가 · basket map 의 raw argmax 가 crate 위에 있는가 · 둘 다인 frame 의 비율.
   - target map 의 crate mass 와 basket map 의 target mass (서로 섞이는 정도).

5. **implementer 는 GPU 를 쓰지 않는다.** unit test 는 합성 probs 텐서로 slicing · 명사 위치 찾기 · reshape (camera 순서) · mass 요약을 검증한다. tokenizer 는 CPU 로 실제 prompt 에 돌려 명사 index 를 검증할 수 있다.

## 이 STEP 이 답하는 질문
**prompt 의 명사 token 이 image 를 보는 attention 은 action token 보다 target 을 더 잘 가리키는가? 그리고 같은 prefix pass 에서 target 과 목적지를 따로 얻을 수 있는가?**

## 되돌아올 지점
- #1 에서 명사 행의 image mass 가 거의 없으면 (text / BOS sink) 명사 query 는 쓸 수 없다. 이때 query 를 "Action:" 직전 token 등으로 바꾸는 것은 별도 판정으로 한다.
- 2D 는 좋은데 3D 가 L8H2 와 같으면 head 처럼 3D 집계가 흡수하는 것이다. 이득은 **목적지 분리 · 결정성 · 비용** 쪽에서만 주장한다.
- prompt 교체에서 map 이 옮겨가지 않으면 명사 map 은 instruction 이 아니라 장면의 현저한 물체를 따르는 것이다. → wrong-object 진단 (검토 문서 §3 후속 후보) 에는 쓸 수 없다.
- 서빙 반영 (`attention_policy.py` 의 source 교체) 은 이 STEP 에서 하지 않는다. 결과 보고 → 사용자 판정 → 별도 STEP 이고, T46 session 에 먼저 알린다.
