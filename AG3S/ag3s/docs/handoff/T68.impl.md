## 결론 — closed-loop 없이 바꿔도 되는가

- 동작 (TrajOpt 가 내는 궤적 · 닫기 명령 · HOLD) 측면에서는 **closed-loop 확인이 필요 없다고 본다.**
  - V1a: 같은 재생에서 557 / 557 bit 동일 (마지막 60 mm 216 / 216). 남긴 A4 39 요청과 여러 초기값 발동 1 요청도 포함이다.
  - V1b: 최종 구성 1,462 요청에서 두 항이 TO 목적함수에 목표 행을 넣은 적이 0 이다.
  - V1b · V1c: G1 의 다른 출력 (배율 · 연속성 끔 · 닫기 gate · HOLD) 도 0 이다.
  - 그러므로 측정된 최종 구성 성능은 T68 인자에서도 그대로 성립한다고 본다. task §3 규칙 "V1 이 통과하면 closed-loop 재측정은 하지 않는다" 에 해당한다.
- 남는 차이 두 가지 (어느 것도 궤적을 바꾸지 않는다):
  1. **벽시계:** 요청당 G1 계산 (중앙 11 ms, p95 164 ms) 이 사라진다.
     - TO budget 시계 밖이고 closed-loop 시뮬레이션은 응답을 기다리며 멈춰 있다. 그래서 궤적에는 영향이 없다.
     - 지연 시간 측정 수치 (`timing_ms.trajopt` · `total`) 는 바뀐다. 표에 쓴 T68 수치는 추정이다. 실측이 필요하면 독점 GPU 로 짧게 재야 한다 (사용자 판정).
  2. **기록 · config · 시작 줄 키:** V1c (3) 에 적은 것들. 기록을 읽는 분석 스크립트 가운데 `grasp.geo` · `grasp.anchor` · `hsr6.detail.objective.a4_withdrawn` 을 세는 것은 T68 run 에서 0 · 없음으로 읽힌다.
- 범위 한계 (적어 둠):
  - 이 동등성은 "최종 구성이 실제로 만난 요청" 위의 것이다. 새 장면에서 ④ 가 HSR6 = grasp 이면서 A4 의 목표 행 (latched, 0 < close row < 16) 이나 G1 보정을 남기는 요청이 생기면, T68 은 그 항 없이 푼다.
  - 이것은 T68 이 의도한 변경 자체다 (부작용이 아니다). 1,462 요청에서는 한 번도 없었다.
- 구성 문서 (`ADOPTED_KO.md` A8 서버 인자 한 줄) 를 T68 인자로 바꾸는 것은 task §3 대로 사용자 확인 뒤 A 가 한다. 나는 문서를 고치지 않았다.
