## 0. 사용자 판정 (2026-11-02)

- "ATS 테스트할 때는 HSR 꺼두고, strong rule 로 단계 나누고, 규칙 적용해볼래?" → 단계 규칙은 **MuJoCo 정답 단계 (분석용)** 로 고름 (질문 선택).

## 1. 근거 (T78 기준선 허들 954, 2026-11-02 읽은 기록)

- 허들 954 의 요청 16–20 (영상 8–10 s, 쥘 손이 사과로 내려가는 중) 에서 TrajOpt 가 손을 참조 궤적에서 5.4 → 11.7 mm 밀었다.
- 밀린 이유: 손가락이 이웃 과일 voxel (정답 라벨 fruit, 24 개 모두 사과보다 이웃 과일에 가깝다) 에서 margin 10 mm 안으로 들어갔다. 사과의 잔여 voxel 이 아니다.
- 같은 요청들에서 단계 분류기 (HSR6) 는 approach, latch 는 이미 latched 였고 기록 `hsr6.detail.objective = {"nbc_withdrawn": true}` 였다. 즉 ④ (이웃 접촉 허용은 grasp 단계에서만) 가 손가락 이웃 허용 (`--neighbour-contact-mm 20`) 을 거뒀다.
- 질문: 단계가 맞으면 (정답 단계) 이 밀림이 없어지는가, 그리고 다른 장면에서 규칙 ①–④ 가 어떻게 달라지는가.

## 2. 구현 (기본 꺼짐 flag, 꺼짐 = 지금과 bit 동일)

- 서버 flag `--hsr-gt-stage` (config 필드는 기존 `--hsr5` 와 같은 자리에 둔다).
  - 필요한 것: `--safe-gt-stage` 로 뜬 client, `--hsr6-*` 4 flag 중 하나 이상 (`--hsr5` 와 같은 조건). `--hsr5` 와 같이 못 쓴다 (둘 다 stage 출처이므로 시작 거절).
  - 켜면: 요청마다 client 가 보낸 정답 5 단계 (approach · grasp · carry · place · retreat) 를 `result["hsr5"]` 와 **같은 모양의 record** (`{"p": 원-핫, "argmax": stage, "probe": "gt"}`) 로 `SafePolicy._hsr5_start` 에 넣는다. 그 뒤는 `--hsr5` 와 같은 코드 (stage → 규칙 연결, `hsr5.py` 의 `SUBTASK3` · `RULE_PHASE6` · `AFTER_GRASP_STAGES` · `CLOSING_KEEP_STAGES`) 를 **그대로** 쓴다. 새 규칙을 더하지 않는다.
  - HSR6 · HSR5 probe 는 이 모드에서 로드하지 않는다 (분류기 끔). 기록은 `hsr5` 아래 `"source": "gt"` (또는 `probe: "gt"`) 로 남기고, 단계 정확도 비교용으로 `hsr6.phase` 는 쓰지 않는다.
- client flag `--safe-gt-stage` (`integration/rby1/bringup/pi05_infer.py`, 기존 `--safe-oracle-seg` 와 같은 방식으로 obs 에 싣는다).
  - 정답 단계 정의 (T77 `t77_labels.phase5_sequence` 와 같은 정의, 요청마다 **인과적으로** 계산):
    - held = 쥐는 손의 두 손가락이 사과에 닿음 ∧ 사과 중심이 요청 0 보다 ≥ 20 mm 올라감 (`gt_held`).
    - held ∧ 사과 중심이 바구니 바닥 xy 범위 안 → place, held 아님 → carry.
    - 한 번 held 였다가 지금 held 아님 → retreat.
    - 아직 held 가 아니었다: 쥐는 손 손바닥 site – 사과 중심 ≤ 60 mm → grasp, 아니면 approach.
  - 계산 함수는 `t77_labels` 의 순수 규칙을 재사용하고 (복제 금지), client 가 MuJoCo state 에서 값을 읽는다. 요청 사이 상태 (ever_held) 는 client 에 둔다.
- 기록: 요청마다 `summary_json.hsr5.source = "gt"` · 단계. 서버가 stage 를 못 받은 요청은 기존 "label 없음" 처리.

## 3. 검증

### 3.1 단위 (implementer)

- 꺼짐 = 지금과 bit 동일 (기록 키 · 결정이 같음). 함수를 켜면 터지게 바꾸는 방식 (T78b · T78d 와 같음).
- 켜짐: GT stage → `rule_phase6` 가 `--hsr5` 와 같은 값. 둘 다 켜면 시작 거절. `--safe-gt-stage` 없이 서버 flag 만 켜면 거절.
- 단계 정의: `phase5_sequence` 와 같은 열을 client 쪽 인과 계산이 낸다 (같은 입력 열로 비교).

### 3.2 closed-loop (lead, 결과 전 고정)

- 구성 S12 = T78f 구성 (S9cl: 표면 추출, 분할 없음, hull 채우기, 접촉 여유 10 mm) 에서 `--hsr6-*` 4 flag 는 그대로 두고 `--hsr-gt-stage` + client `--safe-gt-stage` 를 더한다. 분류기 probe 는 쓰지 않는다. 같은 10 run · 같은 seed.
- 비교: S9cl (분류기 켬, 같은 10 run) · T74 Q1 (공 방식, 8 / 10) · T78 S3 (5 / 10).
- 통과 (모두, T78f §7 과 같음):
  1. 금지 접촉 없는 성공 ≥ 7 / 10.
  2. 금지 접촉 run ≤ 1.
  3. 탁자 · 바구니 접촉 run 0.
- 보고만:
  - 허들 954 요청 16–20 에서 `nbc_withdrawn` 이 false 인지, 쥐기 전 손 밀림 (TCP 수정 크기) 이 5 mm 아래로 내려갔는지.
  - 단계별 (approach · grasp · carry · place · retreat) 요청 수, 분류기 켠 S9cl 과 정답 단계가 갈린 요청 수, 갈린 요청에서 어느 규칙 (① ② ③ ④) 의 결정이 바뀌었는지.
  - 실패 run 의 원인 층 (ATS · HSR · LTE · CCR).
- **target 잔여 측정 정의 (사용자 판정 2026-11-02, 이 STEP 부터 모든 측정):** 정답 사과 표면 voxel 중 **바닥 띠 (지지면 guard 아래: 정답 사과 바닥 z + 6 mm 이하) 는 분모와 분자에서 모두 뺀다.** 바닥 띠는 탁자를 지우지 않으려고 **지금처럼 일부러 남긴다** (guard 를 낮추지 않는다, 규칙 LTE-16 그대로).- 정답 단계는 상한이 아니다 (oracle ≠ 상한). 분류기 오차가 아닌 이유로 실패한 run 은 그 층에서 따로 적는다.
- 통과해도 32 run 은 사용자에게 묻고 간다. 미통과면 숫자를 보고하고 멈춘다.
