## 무엇을 했나 (평이한 요약 먼저)

T54 의 8 개 arm (L8H2 · N · A · B · L12H4 · A-L12H4 · N-k3 · A-k3) 을 **서빙 grounding 코드 그대로** 재생하는 study 를
**새 파일 4 개로만** 추가했다. arm 은 attention map 이 맡는 역할 셋 — primary (lifting · seed · 군집 · peak) ·
split (attention split 비율 gate) · choice (target 을 고르는 점수) — 중 무엇을 어느 map 이 맡는지로 정의된다.
primary 는 서빙 입력 (`attention=`) 으로 넣고, split · choice 는 `process_multi_debug` 호출 한 번 동안만 module
attribute 3 개를 감싸는 **study 쪽 hook** 으로 바꾼다. 서빙 파일 (`pipeline.py` · `target_grounding.py` ·
`attention_split.py` · `config.py` …) 은 한 줄도 고치지 않았다 → lead 보고 대상 아님.
재생 조건은 둘이다: `current` (frame 마다 `AG3S.reset()`, history 없음, 주 조건) · `hold` (arm 마다 자기 AG3S,
T53 은 기록된 서빙 chunk 의 latch 입력을 모든 arm 에 똑같이 주입). 집계 · bootstrap · T57 진입 표는 `t54_stats` 에
사전 고정 그대로 넣었다.

**task 와 다른 점 (lead 판단 필요) — dev parity 의 조건.** task 는 "held-out 4 record 의 L8H2 · N **현재 frame**
재생이 T51b · T52 행과 같아야 한다" 고 적었으나, T51 · T51b · T52 의 행은 **연속 재생 + TargetConfirm** (source 당
AG3S 하나, `t47b_replay._build`) 으로 만든 것이다 (T52 follow-up 이 그 유지 효과를 직접 측정했다). 그래서 현재 frame
재생은 그 행과 같을 수 없다. 실제로 smoke (headfix 15 frame) 에서 `current` 는 T52 와 L8H2 6 frame · N 13 frame 이
다르다 (N 은 identity 1 frame 포함). 그래서 parity 는 **`hold` 조건 + 주입 없음 + t52 profile** (= T51b · T52 와 같은
loop) 에 걸었다. 이 smoke 에서 L8H2 · N 둘 다 mismatch 0/210 이다. `current` 와 T52 의 차이는 정보로만 `parity.json`
에 남긴다.

### arm 과 hook 의 정확한 정의

| arm | primary (서빙 입력) | split ratio gate 가 읽는 값 | choice 점수 (`target_score`) |
|---|---|---|---|
| L8H2 | l8h2 | 서빙 그대로 (= l8h2) | 서빙 그대로 |
| N | noun | 서빙 그대로 (= noun) | 서빙 그대로 |
| **A** | l8h2 | 서빙 그대로 (= l8h2) | **noun 질량** = noun map 을 같은 fused cloud 에 lift 한 정규화 attention 의 cluster 점 합 |
| B | noun | **l8h2** (C1a 는 raw, t52 profile 은 정규화값) | noun 질량 |
| L12H4 / A-L12H4 | l12h4 | l12h4 | 서빙 그대로 / noun 질량 |
| N-k3 / A-k3 | noun_k3 / l8h2 | 서빙 그대로 | 서빙 그대로 / noun_k3 질량 |

알아 둘 상호작용 (코드 docstring 에도 적음):
- A · B 의 `target_score` 는 질량 (합, 보통 ≫ 1) 이다. `TargetConfirm.select` 는 challenger frame 에서 `target_score ≥
  clustering.switch_min_score` 를 본다 (hold 조건만). 질량이면 이 하한은 사실상 걸리지 않는다. 그 밖에 `target_score`
  를 판단에 쓰는 곳은 `target_score_threshold` (기본 0) 뿐이다.
- B: split 의 component 순서 (어느 쪽이 split 의 "target" 인가) 는 primary (noun) 질량으로 정해진다.
  `split_by_attention` 은 `ratio_attention` 을 **비율 gate 에만** 쓴다. 서빙 코드에서 "split 비율이 L8H2 를 읽는다" 의 뜻이 이것이다.
- `current` 는 `reset()` 이므로 destination registry · subtask debounce · 이전 frame 의 target guard 도 없다.
  C1a 의 subtask gate 는 켜져 있지만 debounce (3 frame) 가 확정되지 않으므로 current 에서는 작동하지 않는다.
- `hold` 는 `attach` / `detach` 를 재생하지 않는다 (붙는 기하가 서빙 arm 자신의 target 이므로 robot feedback 이 아님).
  T53 은 16 episode 중 13 개에서 attach 가 1 회씩 있었다 (attached chunk 2 – 20 개). 그 chunk 에서는 서빙과 달리 쥔 과일이
  self-filter 로 지워지지 않고 cloud 에 남는다. 이 점은 모든 arm · 두 조건에서 같다. 기록된 `decision.frozen` 과 주입한
  `grasp_active` 는 16 episode 모두 같다 (`frozen_recorded_ne_grasp_active` = 0).
- 처리 시간은 CPU replay (OMP 1 thread) 의 lift + grounding 이다. **attention 추출 ms 는 이 replay 가 재지 않는다.**
  e2e 는 verifier 가 같은 장치에서 잰 kind 별 추출 ms 를 `--extract-ms '{"action": .., "noun": .., "noun_k3": ..}'` 로 줄 때만
  계산된다. 참고로 T53 noun extract 의 `prefix_ms` 는 3 query 한 prefix pass 를 따로 돈 값이고 median 이 약 24.4 ms 다
  (`inputs.json` 의 `noun_prefix_ms_median`). 서빙에서 명사 행만 더 읽을 때 드는 비용의 상한이다.
