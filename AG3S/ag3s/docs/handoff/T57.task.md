## 단계 2 구현 명세 — HELD 중 task-aware 실행 gate (사용자 판정 2026-10-14, B 작성 → A 구현)

> writer: lead (세션 B, `ag3s-vla-development-c4`) · 2026-10-14 KST · 읽는 쪽: 세션 A (서빙 구현 · 실행).
> 근거: 사용자 판정 2 (2026-10-14): "HELD 중 task_not_ready → HOLD 를 T57 단계 2 의 실험 후보로 승인. 명세를 작성해 A 에 넘긴다."
> 이 승인은 **명세 작성 · A 이관 · 실험 후보 구현** 에 대한 것이다. 기본 서빙 채택은 closed-loop 결과를 보고 판단한다.

### 명칭과 주장 범위

- 이름은 **"HELD 중 task-aware 실행 gate"** 다. "운반 · 놓기 단계 전환" 이나 "placement 완료 인증" 으로 설명하지 않는다.
- 배경 (B 의 코드 확인, `903ea167`): 현재 서빙에는 grasp 이후 운반 · 놓기 단계로의 전환을 승인하는 지점이 없다.
  - `ag3s/types.py` `Phase` 는 외부에서 주입된다 ("AG3S deliberately contains no transition logic").
  - grasp 이후 AG3S 가 바꾸는 것은 latch HELD 에서의 attach 와 identity freeze (`safe_policy._scene_fn` → `set_grasp_active`) 다.
  - HSR subtask gate (`TargetConfirm`, `clustering.subtask_gate`) 는 freeze 가 아닐 때만 작동한다 (`target_grounding.py` "Not while a grasp is in progress (frozen)"). 따라서 HELD 동안에는 영향이 없다.
  - 그래서 새 단계 전환 로직을 만들지 않고, **기존 HOLD 경로** (`SafePolicy._reasons` → `wire.gate_decision`, 사유가 하나라도 HOLD 면 HOLD) 에서 명사 probe 의 실행상 가치를 확인한다.

### 동작 (flag on 일 때)

| 조건 | 동작 |
|---|---|
| latch = **HELD** ∧ task_ready = false | 이번 요청의 `verdict_reasons` 에 `task_not_ready` 사유를 추가한다 → 기존 판정 규칙으로 HOLD |
| latch = HELD ∧ task_ready = true | `task_not_ready` 사유만 없다. 다른 HOLD 사유 (인증 · 위반 · unverified …) 가 있으면 기존 판정을 따른다 |
| latch ≠ HELD (SEARCHING · LATCHED · CLOSING · PLACED) | **기존 동작 그대로.** 사유를 추가하지 않는다. HELD 의 false negative (#48, T55b) 가 HOLD 를 만들지 않는다 |
| 바꾸지 않는 것 | `GraspLatch` 의 attach / detach, `TargetConfirm` (freeze · subtask gate · release), AG3S 의 constraint 계산 |

- **task_ready = HELD ∧ (명사 probe p ≥ τ) ∧ noun_ok**, 지속 p = 1. 모두 T55 prereg 그대로이고 바꾸지 않는다.
  - prereg: `…/20261013T171325+0900_cf38c9dbca7b_2ebfd8a5a43c/verify/T55/T55.prereg.json` (sha256 `8f62fc76…`), `arms.noun`
  - feature `v5` = prefix pass 의 **target 명사 token 행의 layer 5 V cache** (`t53_extract.NounTokenExtractor` · `t55_study.noun_matrix("v5")`, 256 차원)
  - probe = `…/verify/T55/noun_probe.npz` (md5 `648e880d…`, logistic C 0.1), τ = 0.3
  - 명사 token 을 찾지 못하면 (`noun_ok = false`) flag 는 false 다 → HELD 이면 HOLD
- "target 명사" 는 **policy 에 실제로 들어간 prompt 의 명사** 다 (T55 정의).

### 반드시 지킬 것 (사용자 판정)

1. **HOLD 중에도 새 관측으로 정책 · probe 추론이 계속되어야 한다.**
   - HOLD 는 그 chunk 의 실행만 막는다.
   - 다음 요청에서 정책 추론 · prefix pass · probe · latch 갱신은 새 관측으로 다시 돌아야 한다. 실행을 멈추면서 재평가까지 멈추면 재개할 수 없다.
   - 구현 뒤 dev 확인에서, HOLD 가 이어진 요청들의 probe p 와 task_ready 가 요청마다 새로 계산되었는지 기록으로 보인다.
2. **flag off 의 출력 회귀와 shadow 비용을 구분한다.**
   - flag off: 출력 (chunk · verdict · wire digest) 이 현재 서빙과 bit-identical 이어야 한다 (CL3 층 · wire digest · 회귀 기준선 legacy · cuRobo, 단계 1 과 같은 검사).
   - shadow (flag off 이어도 task_ready · probe p 를 계산해 기록만 하는 모드) 를 넣으면 추가 계산이 생긴다. 그 비용은 따로 잰다: prefix pass 안 gather 와 logistic, 또는 별도 pass 라면 그 시간, 요청당 ms · p95. "기본 off 이므로 비용도 같다" 고 쓰지 않는다.
   - shadow 를 기본으로 켤지는 A 가 비용을 보고 정한다. 측정 실험의 gate arm 은 flag on 이다.

### dev 확인 (→ A, T57 단계 1 이후 같은 설정, 작은 규모)

- 비교: 단계 1 결과의 서빙 설정 위에서 gate 만 켠 arm 을 같은 episode · seed 로 돌린다.

  1. **정상 target 을 쥔 경우:** 불필요한 `task_not_ready` HOLD 가 생기는가, 생기면 재개되는가 (HOLD 길이 · 재개 시점 · 그동안의 probe p)
